# 央视频TV（yangshipin-tv）

安卓电视端直播 App。用 WebView 打开 `https://www.yangshipin.cn/tv/home`，**只保留「视频播放器 + 选台列表」**，其余（顶部导航、搜索、页脚、节目单、各类弹层）全部砍掉。

此外还内置一个**「自定义源」播放器**：原生 `VideoView` 播自己导入的 m3u8 / mp4 —— 见 [自定义源](#自定义源播自己的-m3u8--mp4)。

## 自定义源（播自己的 m3u8 / mp4）

除了央视频直播，App 里还有一个**独立入口**「自定义源」，用来播自己找的流地址

> 这是和主界面**并列的第二个 Activity**，不是主界面里的一个弹层 ——
> 因为它是**原生 `VideoView` 播 HLS**，而不是 WebView 播央视频页面，两套渲染通路不能混。
>
> **怎么进去**（1.5.1 起，第 ① 条是特意补的）：
> ① **按确认键打开选台面板，最上面那行就是「自定义源」** —— 光标在第 0 台再按一次上键即可到达，按确认进入；
> ② 蓝色功能键；③ 菜单键长按 0.7 秒。
> （1.9 起电视桌面上只有「央视频TV」**一个**图标，见 [§33](#33-v19单图标--剪贴板导入--去掉内置示例源)。）
>
> **进了这一页之后，怎么添加源**（1.8 起补的可见入口）：
> **按确认键打开选台面板，最上面那行是「＋ 添加自定义源」** —— 光标在第 0 台
> 再按一次上键就到它，按确认直接打开「源管理」浮层（局域网导入 / 剪贴板导入 /

### 四条导入路径

| 方式 | 适合 | 说明 |
|---|---|---|
| **从网址导入** | 聚合清单（几十~几千条） | 给一份 **m3u 清单的网址**（例如 `https://…/cn_all.m3u8`），**由电视自己去抓**、解析、整份导入。抓成功就把这个地址记住，以后可以一键刷新。入口有两处：局域网导入页的第一个输入框，以及电视上「菜单 → 刷新远程清单」 |
| **从剪贴板导入** | 手机上刚复制好的东西 | 电视上**没有任何「粘贴」键**，屏上键盘是一个字符一个字符敲。所以在手机上复制一段 m3u（或一条地址），电视这边「菜单 → 从剪贴板导入」按一下就进来了：单行网址按一条源收，多行文本按整份清单解析（**不联网**） |
| **局域网粘贴** | 手上已经有一份清单文件 | 电视上打开「源管理」时会起一个临时 HTTP 服务，**手机上浏览器打开那个地址**，把 M3U 内容粘进第二个框。地址形如 `http://192.168.1.x:34567/` |
| **屏上键盘** | 临时加一条直播地址 | 遥控器方向键打字，57 键（50 字母数字 + 7 功能键）。带协议白名单校验。**填一份清单的网址也行** —— Android 侧会先抓一遍，是清单就整份导入，是一路流就收下这一条 |

> **1.9 起没有内置示例源了**（原来那条「5 条公开测试流 / 恢复内置示例源」已整条删除）。
> 零源时的落地页是**直接打开的「源管理」浮层**，配一条常驻提示告诉你三条路怎么走；
> 关掉浮层提示仍在（零源时选台面板根本开不起来，提示要是跟着没了就只剩黑屏）。
> 见 [§33](#33-v19单图标--剪贴板导入--去掉内置示例源)。

「从网址导入」的判断规则（`M3uParser.looksLikeChannelList`）值得写清楚，因为**光看地址分不出
一个 URL 是「频道清单」还是「一路直播流」**（两者常常都以 `.m3u8` 结尾）。所以先抓，再看内容：

| 抓回来的内容 | 处理 |
|---|---|
| 频道清单（≥2 条台，或 1 条但带 `#EXTM3U`） | ✅ **整份导入**，并记住清单地址 |
| 单个流自己的清单（`#EXT-X-TARGETDURATION` 等） | 把它当**一条源**收下 —— 地址本身就是能播的东西 |
| 一张网页（登录页 / 「源已失效」提示页） | 同上，按一条源收下，提示里说明「抓回来是网页」 |
| 抓不到（断网 / 403 / 404 / 超时） | 同上，按一条源收下，提示里说明抓取失败的原因 |

> 「抓不到也照收」不是偷懒：有些源就是要特定请求头、或者只在播放器里才拉得起来，
> **抓取失败 ≠ 播不了**。这一条同时也是为了不破坏 1.2 之前的行为。

想先摸清一份清单值不值得导，用 `node tools/iptv_list_probe.mjs <清单URL>`（离线体检）：
逐个探测可达性，并标出 `#EXT-X-MEDIA` / fMP4 / 加密这些会让框架 HLS 翻车的特征。

### 播不通会自动换同一台的下一路（v1.4）

聚合清单里同一个台常有好几路地址，而这类清单**约 1/3 是死链**
（在这份 `cn_all.m3u8` 上实测：181 条里 162 条属于「有镜像的台」，
宿主侧探活有 35 条不通）。所以：

* 点了一条播不出来 → **自动试同一个台的下一路**，状态层显示「这个台的第 2/4 路地址…」；
* 换成功了会弹一句「这一路不通，已自动换到「CCTV-1」的第 2 路地址」；
* 试满 **4 路** 或整轮超过 **40 秒** 才收手，报失败时写明「这个台一共 N 路地址，已经试过 M 路」；
* 失败过的地址在列表里会**变暗并打 ⚠**，下次顺延优先挑没失败过的那几路。

**「同一个台」是按归一化后的台名判的**，所以 `CCTV1` / `CCTV-1` / `CCTV-1 (720p)`
算同一个台（真实清单里它们合起来有 6 路），而 `CCTV5` 和 `CCTV5+` **是两个台**。
规则与取舍见「实现要点 25」。

**两处刻意不自动换台的场合**：你打开了「源管理」浮层时（那是「我要接管」的信号），
以及点播流正常播完时（那不是失败）。两条都有测试钉着。

局域网导入是**手写的 HTTP/1.1**（`ServerSocket` 绑 `0.0.0.0:0` 拿临时端口），不引任何依赖；
单线程串行 accept、**只在「源管理」浮层打开时监听**、无鉴权 —— 见「已知限制」。

### 能播什么、不能播什么（实测，不是推测）

Android 的 WebView **没有原生 HLS**（`<video src="x.m3u8">` 什么都不会发生），
网页里播 m3u8 只能靠 hls.js，而 hls.js 依赖 MSE。实测：
Chromium 12x（API 34）上 hls.js 1.5.20 / 0.14.17 都能完美播放；
但 Chromium 37（API 21）上 1.5.20 直接 `internalException` 挂掉、0.14.17 能解出画面数据却渲染不出来。
**所以这里走的是原生 `MediaPlayer`/`VideoView` 的 HLS 通路**（系统框架 `libstagefright`，
不依赖 MSE/WASM，也不引第三方库，零依赖得以保住）。

| 情形 | 结果 |
|---|---|
| `#EXTINF` + `.ts` 分片（最常见） | ✅ |
| 多码率 master 列表（`#EXT-X-STREAM-INF`） | ✅ 自动挑一路 |
| AES-128 加密（`#EXT-X-KEY`） | ✅ 一般可以 |
| **带备用音轨的多音轨 master（`#EXT-X-MEDIA`）** | ⚠️ **最容易翻车的一种**，见下 |
| fMP4（`#EXT-X-MAP` + `.m4s`） | 需要 **Android 8+**；老盒子大概率不行 |
| rtsp / rtmp / udp | 交给系统播放器，能不能看设备厂商的实现 |

> ⚠️ **多音轨（`#EXT-X-MEDIA`）是实测踩出来的头号雷区。**
> 框架的 HLS 解封装在「一个视频 + 多条备用音轨」的 master 列表面前会翻车，
> 而且翻车方式很迷惑：**能起播**，然后 2 秒内 mediaserver 直接死掉。
> 内置示例源（1.9 已删除，但这条规矩对**用户自己导入的地址**同样成立）踩过这个
> —— 见「实现要点 19」，挑测试流有一条硬规矩。

### 局域网导入的安全边界（诚实交代）

- **没有鉴权**。同一个局域网里任何人打开那个地址都能读写你的源列表。
  所以服务**只在「源管理」浮层打开时**监听，关掉浮层立刻 `stop()`。
- 请求体上限 4 MB，只解析 M3U，**不落任何文件、不执行任何脚本**。
- 导入的地址只影响**本 App 自己的源列表**，不碰系统、不碰别的 App。
- 页面对写入的内容一律走 `textContent`，不拼 HTML（防 XSS）。
- **它不能被当成通用代理用**：`/api/addurl` 抓的地址必须过协议白名单（只放 http/https），
  抓回来的内容**不会回显给请求方**，只会变成源列表里的条目；正文还有 2 MB 上限
  （`PlaylistFetcher.MAX_BYTES`），所以拿它去拉大文件是拉不动的。

## 实现要点（踩过的坑，改代码前务必看）

### 1. 必须伪装桌面 UA —— 否则整个方案不成立
站点首页脚本里有 `isMobile()` 检查，UA 命中 `Android|Mobile|TV|pad...` 就会被 `window.location.replace`
重定向到移动站 `m.yangshipin.cn`，那里没有电视直播布局。
`MainActivity` 里写死了 Windows Chrome UA。**不要改成默认 UA。**

### 2. 目标 DOM：只留两个容器

```
.tv-main
└── .tv-main-con                    ← 唯一保留的区域
    ├── .tv-main-con-l              ← 播放器（钉在左侧，right:21vw）
    │   └── .tv-main-con-l-vid > video
    └── .tv-main-con-r              ← 选台面板（钉在右侧，width:21vw）
        ├── .tv-main-con-r-tab      ← CCTV / 卫视 切换
        └── .tv-main-con-r-list
            └── .tv-main-con-r-list-left   ← 频道行容器（注意！见下）
```

砍掉：`.header`（顶栏+搜索）、`.footer`、`.tv-zhan`（节目单）、各种 `win*-mask` 弹层。

### 3. ⚠️ 最大的坑：频道容器里装着「两份名单」

`.tv-main-con-r-list-left` 里**同时**存在两组行：

- `.tv-main-con-r-list-left-imga` → **40 个央视频道**
- `.tv-main-con-r-list-left-imgb` → **33 个卫视频道**

站点用 **`display:none`** 隐藏非活动那一组。由此推出两条铁律：

- **CSS 里绝对不要给这些行设置 `display`。** 一旦写成 `display:flex !important`，
  会把两组合并渲染 → tab 失效、列表出现 73 项、方向键会走进隐藏项。
- **JS 取行必须过滤可见性**（`offsetParent !== null`），否则选台会选到看不见的频道。

### 4. 行的文字颜色在 `span` 上，不在行上
行 `.tv-main-con-r-list-left-imga` 自身 `color` 是黑的，文字在 `<span>` 里。
颜色/字号必须写到 `.tv-main-con-r-list-left > div > span`。
另外 span 自带 `line_tv_box.svg` 背景装饰，需要 `background-image:none` 干掉。

### 5. 方向键必须自己实现
WebView 不会给 `div` 列表自动移动焦点，所以 `inject.js` 维护一个 `idx` 光标：
- `.ysp-focus` = 遥控光标（深灰底 + 红色左侧条）
- `.tvSelect` = 站点维护的「正在播放」（红底白字）

两者刻意分开：切到卫视 tab 时，正在播放的 CCTV 频道不在本组，因此本组无红标，这是正确表现。

### 6. 页面是 SPA
路由切换不会触发 `onPageFinished`。所以注入是**幂等**的，并且在
`onPageFinished` + 多个延时点重复注入；`inject.js` 内部还有 `MutationObserver` 兜底补回光标。

### 7. ⚠️ 清场规则里必须放行提示气泡，且气泡要挂 `body` 不能挂 `#app`
清场规则是 `body > *:not(#app):not(#ysp-toast) { display:none }`。
那个 `:not(#ysp-toast)` **不能删**，否则直接挂 `body` 的气泡会被自己的规则隐藏
（现象很隐蔽：`getComputedStyle` 读到的 `opacity` 仍是 1，但元素实际不可见）。

挂载位置也有讲究 —— **必须挂 `body`，不要挂 `#app`**：
站点首屏会把 `#app` 的内容整体重渲染一遍，挂在里面的气泡会被连带清掉。
这个坑更隐蔽：`localStorage` 的一次性标记已经置位（说明代码跑过了），
可气泡从头到尾没出现过一次。挂 `body` 就绕开了重渲染。

### 8. 面板用 transform 隐藏，不要用 display:none
面板收起是靠 `transform: translateX(-101%)`，元素仍在文档流里。
这样频道行的 `offsetParent` 始终不为 null，`rows()` 的可见性过滤才能正常工作 ——
若改用 `display:none` 隐藏面板，收起状态下上下键会取不到任何频道。

### 9. ⚠️ 列表上下边缘会露出「半行」——行高必须凑成整数行 + 滚动对齐整行
两个独立成因，缺一不可：

- **底边半行**：列表可视高（`100vh - tab高`）除以行高除不尽。
  例如 1080p 下 `993 ÷ 77.8 = 12.77` 行 → 第 13 行只露 77%。
  **解法**：`inject.js` 的 `fitRows()` 把 `--row-h` 重算成 `可视高 ÷ round(可视高/行高)`，
  让一屏正好装下整数行，余数归零。
- **顶边半行**：`scrollIntoView({block:'center'})` 会把滚动位置停在两行之间。
  **解法**：`scrollToRow()` 直接算 `scrollTop = base + top * rowH`，强制对齐到行高整数倍。

配套约束：`.tv-main-con-r-list-left` 的上下 `padding` **必须为 0**。
有 padding 时滚动坐标系原点会偏移，行对齐公式就失效了（改用实测的 `base` 兜底，
但 padding 归零后 `base` 恰好为 0，公式最直观）。

实测：模拟器（2400×1080）12 行、1080p（1920×1080）13 行，上下边缘偏差均 < 0.8px。
回归断言见 `tools/device_test.mjs` §10 与 `tools/interact.mjs` §11。

### 10. ⚠️ 改了 `tools/inject.*` 一定要同步到 `assets/`
`MainActivity` 从 `assets/` 读 `inject.css` / `inject.js`，而且**首次读取后会缓存在字段里**，
之后每 15 秒用它重新注入一次。所以：

- 只改 `tools/` 下的源文件，APK 里仍是旧版 → 白折腾；
- 用调试通道热更 CSS 也撑不过 15 秒 —— 会被缓存里的旧 CSS 覆盖回去。

`build.sh` 已内置同步步骤（`cmp -s` 比对后 `cp`），改完直接 `bash build.sh` 即可。

### 11. ⚠️ 字号必须按 TV 观看距离给 —— 手机模拟器上「看着还行」不等于电视上能看
在手机 AVD 上测时一切正常，换到真 Android TV 后才发现**台名字号明显偏小**。

原因是踩了 `vh` 的坑：手机 AVD 与 1080p 电视**物理高都是 1080px**，但 dpr 不同
（手机 2.625 → 视口 411px；电视 2.0 → 视口 540px）。
按 `vh` 给字号时，两者算出的**物理字高恰好相同**，所以手机上不会露馅；
可 2.1vh 只有 22.6 物理 px，约合 11sp —— 远低于 Android TV 的阅读标准（正文 16sp 起）。

**结论：**
- 面板字号走 CSS 变量 `--char-size: 3.2vh`（1080p 下 ≈34.6 物理 px ≈ 17sp），别改小；
- 行高初始 `--row-h: 7.6vh`，由 `fitRows()` 收敛成整数行（1080p 电视上正好 12 行）；
- 判断「字号够不够」永远用**物理像素**，不要被 CSS 像素骗了：
  `字号物理px = fontSize × devicePixelRatio`。
  `tools/device_test.mjs` §12 已把这条固化成断言（物理字高 ≥30px、字/行 ∈ [0.35,0.55]）。

顺带修掉一个相关问题：两个 tab logo 原来只给了 `max-height`，
CCTV 宽字标和卫视图标各按自己的宽高比缩放，看起来一大一小；
改成定高 `height: 4vh` + `object-fit: contain` 后两者严格等高。

### 12. ⚠️ 自动横屏：手机和电视要的**不是同一种横屏**
这套界面是给电视做的，手机竖屏完全没法用。所以两端都强制横屏，但取值不同：

| 设备 | 取值 | 理由 |
|---|---|---|
| 电视 / 平板（sw≥600dp） | `SCREEN_ORIENTATION_LANDSCAPE` | 面板竖不起来，但有些盒子带重力感应，方向抖动会让画面莫名翻转 → 硬锁 |
| 手机 | `SCREEN_ORIENTATION_SENSOR_LANDSCAPE` | 强制横屏，同时允许用户把手机调个头握持时画面跟着转（只在左右横屏间二选一） |

**关键取舍：不要用 `SENSOR` / `FULL_SENSOR` / `USER` / `USER_LANDSCAPE`。**
那几个会尊重系统的「自动旋转」开关 —— 用户在设置里把旋转锁成竖屏后，App 就真的竖起来了。
`LANDSCAPE` / `SENSOR_LANDSCAPE` 是硬性声明，会直接压过系统旋转锁。

实测（`tools/phone_orientation_test.mjs`，11/11 通过）：
- `accelerometer_rotation=0` + `user_rotation=0`（系统锁死竖屏）冷启动 → 屏幕仍是 **2400×1080 横向**；
- 打开自动旋转后往加速计灌「竖屏直立」→ 仍是横向，`mDisplayRotation` 只在 90/270 之间，**从不落到 0/180**；
- 向左倒 → `ROTATION_90`，向右倒 → `ROTATION_270`，翻转生效。

**别把「没有触摸屏」当电视判据。** 实测 TV 模拟器（`sdk_google_atv64_arm64`）
同时声明了 `android.hardware.touchscreen` / `faketouch` / `multitouch` 全家桶，
而不少真手机反而不声明 baseline 的 `android.hardware.touchscreen`。
主判据必须是 `android.software.leanback` / `android.hardware.type.television`。

另外 `android:configChanges` 里的 `orientation|screenSize` **不能删**：
方向变化若不自己处理，系统会重建 Activity，WebView 里的直播会被打断重连。
实测方向来回切换后 `ActivityRecord` 实例哈希始终不变。

### 13. ⚠️ 全屏沉浸别再用 `setSystemUiVisibility`
老的 `SYSTEM_UI_FLAG_*` 已废弃，在 Android 14/15/16 上会被系统忽略，状态栏会一直挂着。
现在走 `WindowInsetsController`（API 30+），低版本才回落到老 flag：

```java
WindowInsetsController c = getWindow().getDecorView().getWindowInsetsController();
c.hide(WindowInsets.Type.systemBars());
c.setSystemBarsBehavior(WindowInsetsController.BEHAVIOR_SHOW_TRANSIENT_BARS_BY_SWIPE);
```

配套三处：
- `getWindow().setDecorFitsSystemWindows(false)`（API 30+，等价于老 `LAYOUT_FULLSCREEN|LAYOUT_HIDE_NAVIGATION`）；
- `LAYOUT_IN_DISPLAY_CUTOUT_MODE_SHORT_EDGES`，否则刘海屏横屏时边上留一条黑边；
- 重写 `onWindowFocusChanged()` 再隐藏一次 —— 弹窗/输入法/切回前台后系统栏会自己冒出来。

回归断言见 `tools/device_test.mjs` §13（窗口边界 == 物理屏幕尺寸）。

### 14. ⚠️ 手机必须另做一层触摸手势 —— 遥控器那套在手机上完全用不了
这套界面原本只按遥控器设计（上/下键换台、确认键弹面板）。手机没有方向键，
上线前实测：**轻点、点边缘、上下滑全部无反应**，用户根本没法换台。
所以 `inject.js` 里补了 `initTouch()`，手势映射见上面「手机触摸操作」表。

三个容易踩的点：

- **点频道行不要合成 `click`。** 真实触摸本身就会依次派发
  `touchstart→touchend→mousedown→mouseup→click`，再合成一次等于点两遍。
  （遥控器路径必须合成，因为键盘事件不会产生鼠标事件 —— 两条路径刻意不同。）
- **列表拖动要等惯性滚完再吸附整行。** 在 `touchend` 立刻吸附会把惯性吃掉，
  手感很"粘"。做法是：拖动期间每次 `scroll` 事件都重置一个 260ms 的定时器，
  定时器到期（即停了 260ms 没再滚）才调 `snapScroll()`。另加 2s 兜底清标志位。
  不在列表里拖动 = 不滚动，交给外层手势判定。
- **手指一碰就重置自动隐藏倒计时。** 否则用户在看列表时面板会突然消失。
  `touchstart`/`touchmove` 都调 `armAutoHide()`。

判定轻点 vs 滑动：位移 <22px 且按下 <500ms 算轻点；纵向位移 ≥34px 且大于横向
1.15 倍算竖滑。**上滑 = 下一台**（和列表方向一致，也符合手机上看视频的直觉）。

触摸层在电视上是空转的（永远收不到 touch 事件），所以不需要按设备开关。
唯一按设备区分的是**首次手势提示**：`MainActivity` 注入 `window.__yspTV_TOUCH`，
只有触摸设备才弹，且只在画面真的出来之后弹一次
（等 `video.videoWidth > 0`；站点自带「全力加载中…」期间弹等于白发）。

回归断言见 `tools/phone_touch_test.mjs`（22 项）。
⚠️ 用 `adb shell input swipe` **测不了系统手势**（边缘返回、底部上滑）——
注入事件不经过 SystemUI 的手势识别器，怎么划都没反应。这两条只能在真机上手动确认。

### 15. ⚠️ 老系统兼容 —— 1.6 起**整体不伺候了**（`minSdk 24` / Android 7.0）

> **结论（2026-10-13，1.6 起）：`minSdk 19 → 21 → 24`。老设备不伺候了，
> 「内核能力体检」那整条降级路径一并删除。**
> 下面这一节是一次完整的排查记录，**不再是待办**。
> 三跳各自的原因（别再倒回去）：
>
> | 版本 | minSdk | 为什么这一档 | 代价 |
> |---|---|---|---|
> | 1.4 及以前 | 19 | 让 4.4「装得上、看到一句人话」，而不是卡在「解析程序包时出现问题」 | 「不许用 API 21+ 类型」「图标不许用矢量」两条重纪律 |
> | 1.5 | 21 | 放弃 4.4：站点要 MSE + WASM，最低 **Chrome 57**；4.4 的 WebView 固定 Chromium 30 且编在 framework 里升不了 | 5.0/6.0 上 WebView 未必升过 → 还得养一页「内核能力体检」 |
> | **1.6** | **24** | **老设备整体不伺候**：7.0 起 WebView 是独立可更新 APK，在役设备内核都远高于 Chrome 57；5.0/6.0 那批「装得上、内核可能还停在 Chromium 37」，不值得为它们继续养降级路径 | 无（7.0 以下装不上，也不再给提示） |
>
> **1.6 删掉的东西**：
> `MainActivity` 的 `checkBrowserCapability()` / `showCapabilityError()` /
> `yspBridge.onCapability()` / `capabilityChecked` / `capabilityFailed`，
> 只为那页存在的 `loadingTitle` / `loadingHint` 两个字段，
> `TvShellActivity.realEngineVersion()`，以及 `tools/legacy_capability_test.mjs`
> （已移到 `/tmp/ysp_removed/`，要找回还来得及）。
> 7.0 以下现在会**在安装阶段被直接拒绝**，也不再有「装上但看不见画面」的中间态。
>
> ⚠️ **提到 24 不等于所有 API 隔离都能删。** `Api28` / `Api30` **照旧保留**：
> 24 < 28 < 30，跑在 7.0（API 24）上的设备加载含 API 30 类型的类，
> 一样是 `NoClassDefFoundError`。隔离线跟着 **minSdk** 走，不跟着 compileSdk 走。
> 说「都 7.0 了还隔什么离」是错的 —— 这条在 `Api28` 的类注释里也写了一份。
>
> ⚠️ **v1(JAR) 签名不再是硬要求**（v2 签名是 API 24 引入的，7.0 起全支持），
> 不过默认签名方案仍会同时签 v1+v2，没动它。

**起因**：用户在 Android 4.4.2 电视上装包，报「解析程序包时出现问题」。

**根因**：原来 `minSdk = 21`，而 4.4.2 是 API 19。安装器在**解析阶段**就拒绝了，
所以报的是「解析」错误而不是「版本不兼容」。改 `minSdk 19` 即可。

但改完 minSdk 只是让它**装得上**。实测（下面是真数据，不是推断）：

**a) 站点到底要什么能力？——「能力摘除」消融实验**
在正常播放的 TV 模拟器上，用 `Page.addScriptToEvaluateOnNewDocument` 在页面脚本
执行前把某个 API 抹掉，再刷新看 `<video>` 还能不能拿到画面
（脚本：`tools/browser_capability_probe.mjs`）：

| 摘掉的 API | 画面 | 结论 | 最低内核 |
|---|---|---|---|
| （对照） | ✅ | 基线（`src=blob:` → MSE 在喂流） | — |
| `MediaSource` | ❌ 全黑 | **硬依赖** | WebView 4.4.3 / Chromium 33 |
| `WebAssembly` | ❌ 全黑 + 站点自己弹「请升级浏览器」 | **硬依赖** | Chrome 57 |
| `fetch` | ❌ 全黑 | **硬依赖** | Chrome 42 |
| `Promise` | ✅ 照常播 | 会被 polyfill，非必需 | — |

→ **最低 Chrome 57（2017-03）**。而 Android 4.4.2 的 WebView 是 **Chromium 30（2013-11）**。

**b) 为什么没救**：WebView 变成可独立升级的 APK 是 **5.0 才开始**的，Google 的
WebView 更新也只发到 5.0+。4.4 的 WebView 编在 framework 里，改 App 改不出来。
MSE / WebAssembly 属于**引擎能力，无法用网页脚本 polyfill**。
（注意 4.4.2 卡在一条很尴尬的线上：MSE 是 **4.4.3** 才进的 WebView。）

**c) 实测确认（API 21，WebView = Chromium 37）**
在 Apple Silicon 上起不了真 Dalvik（见下），退而求其次用 API 21 arm64 实测：
站点日志原样打出 `no native wasm support detected` / `WebAssembly is not defined`，
我们的能力体检页正确报出「缺少 WebAssembly · fetch ｜ 内核 Chrome/37」。

**为此做的四件事：**

1. **Dalvik 兼容：API 敏感代码必须拆类隔离（最关键的一条）**
   minSdk < 21 意味着要跑在 Dalvik 上。Dalvik 在**类加载/校验**阶段会解析方法体里
   出现的类型 —— 把 API 30 的 `WindowInsetsController` 写在 `MainActivity` 里，
   4.4 上加载 `MainActivity` 就会 `NoClassDefFoundError` / `VerifyError`。
   **`if (SDK_INT >= X)` 守卫只挡「执行」，挡不住「解析」。**
   所以拆成 `Api21` / `Api28` / `Api30` 三个内嵌类，只有系统版本够才去加载它们。
   同时删掉了两个重写：`onReceivedError(WebView, WebResourceRequest, WebResourceError)`（API 23 参数类型）
   和 `onPermissionRequest(PermissionRequest)`（API 21 参数类型）—— 匿名类是 `MainActivity`
   的一部分，签名里带上新类型同样会在类加载时炸。二者的框架默认实现本来就够用。
   静态把关：`./gradlew :app:lintDebug` 对 minSdk 19 报 **0 条 `NewApi`**。

   > **1.5 变更**：minSdk 提到 21 之后，`Api21` 这一段**整个撤销** ——
   > API 21 的类型（WebView 的 `setMixedContentMode` / `setAcceptThirdPartyCookies`）
   > 可以直接写在 `MainActivity` 里，隔离类删除，相关守卫一并去掉。
   > 但 `Api28` / `Api30` **保留不动**，上面那条类加载纪律对它们依然成立。
   > 另外两条：
   > · `onReceivedError(WebView, WebResourceRequest, ...)`（参数类型 API 23）
   > · `onPermissionRequest(PermissionRequest)`（参数类型 API 21）
   > **1.6（minSdk 24）之后这两条在技术上都可以重写了**，但仍然不重写 ——
   >   框架默认实现本来够用，重写等于抄一遍默认行为，多一份维护成本。
   > 隔离理由本身从 `Api21` 搬到了 `Api28` 的类注释里（免得删文件时把规矩一起删掉）。

2. **内核体检 + 说人话的降级页**（**1.6 已删除**，下面留的是方法论，不是现状）
   曾经的做法：进页面先探测 MSE / WebAssembly / fetch，缺任何一项就显示说明页，
   而不是让用户对着站点的「全力加载中…」干等。
   minSdk 24 之后这条路没必要了 —— 装得上的设备内核都远高于 Chrome 57。
   ⚠️ **取内核版本必须走 Java 侧**（这条方法论保留）：`WebSettings.getDefaultUserAgent()`
   （静态方法，不受实例 `setUserAgentString` 影响）。用 `navigator.userAgent` 会读到
   我们伪装的桌面 UA（**Chrome/120**），实测踩过 —— 提示写着「内核 Chrome/120」等于没说。
   真要再查「这台机器到底缺什么」，用 `tools/browser_capability_probe.mjs`（离线研究用，不进 APK）。

3. **图标：位图 → 矢量（1.5 又反过来了一次，两个方向都对，因为 minSdk 变了）**
   · **1.4（minSdk 19）**：图标**必须**是位图。AAPT2 会把矢量限定成 `drawable-anydpi-v21/`
     （API 21+ 才有），而 minSdk<21 时它还会把每个矢量图烘成一整套各密度 PNG，
     烘出来的比手写位图**更大更差**。所以当时补了一套真 PNG（`tools/gen_icons.py`）。
   · **1.5（minSdk 21）**：AAPT2 不再烘，**一张 1,581 字节的矢量 XML 顶掉五档位图**，
     release 包 115,715 → **104,231**。于是五档 PNG 全部删除，只留矢量。
     横幅 `tv_banner` **仍是位图**：它是 Android TV 主屏的门面，各家 launcher 怎么取
     不一定（有的按位图解码），矢量在这里赌不起。
   ⚠️ **颜色仍然统一用纯色**：矢量的 `<gradient>` 内联颜色要 **API 24** 才支持，
   1.5（minSdk 21）时最低那批是 5.0/5.1，在那儿会解析失败，所以只能用纯色。
   **1.6（minSdk 24）起技术上可以用渐变了**，但图标本来就是「深底 + 红圆 + 白三角」的
   纯色设计，没必要为了用而用 —— 这条记下来，是将来改图标时的一条可选解法。
   验证看**资源表**而不是文件名（release 包会开资源名混淆，`res/M2.png` 那种）：
   ```
   aapt2 dump resources <apk> | grep -A 4 'drawable/ic_launcher'
     () (file) res/drawable/ic_launcher.xml type=XML     ← 只有一条，且是 XML
   ```
   现在钉的是**两条**：「是矢量」**且**「确实没被烘成 PNG」——
   后者才是真正值钱的那半条，见下面第 4 点说的假绿陷阱。

4. **把用户遇到的报错变成可复现断言**
   1.6 之前是 `tools/legacy_capability_test.mjs`（静态 12 + 运行时 10 = 22 项），
   随老设备一起退役了。**「minSdk 到底是多少」「能力体检确实没了」这两条
   现在由 `custom_source_test.mjs` 的静态段接管**（顺带钉住 `Api28` / `Api30` 不许删）。
   ⚠️ **这里踩过两个「假绿 / 假红」**（值得单独记一笔）：
   · **假绿**：第一版断言「AAPT2 没有把矢量烘成 PNG」用正则读资源表，
     结果 `()` 空括号匹配不到、`(file)` 又被当成密度配置项 —— 一条记录都没解析出来，
     于是「没有 PNG」**空跑通过**。修法除了修正则，还加了一条**反向正例探针**
     （要求 `tv_banner` 必须解析出 4 条 PNG 记录）：
     凡是「应该没有 X」的断言，都得配一条「必须解析得到 Y」，否则正则一坏就全是假绿。
   · **假红**：解析源码里的版本号时，**必须先剥注释**。1.6 那次给 `build.gradle`
     写「minSdk 三跳：19 → 21 → 24」的说明，结果 `/minSdk\s+(\d+)/` 抓到注释里的 **19**，
     断言当场红。好在是红不是绿 —— 但同样的坑在 `setVideoURI` 守卫那条上早就踩过一次了。

**⚠️ 本机验不了的那一段（诚实交代）**
真 Dalvik（4.4）需要 32 位 ARM guest，而模拟器在 aarch64 host 上硬编码
「系统镜像必须匹配宿主架构」，`armeabi-v7a` 镜像直接拒启（`-engine classic` 也一样）。

后端，所以 API 19 的 x86 镜像同样跑不了；而 arm64 镜像最早只到 API 21。
→ 4.4 上的实际运行**没有真机验证**，只有：Lint 静态零 `NewApi` + 类隔离 +
API 21 实测（ART，比 Dalvik 校验更严）三者共同支撑。
（不过既然已经决定不做 4.4，这一段现在只是历史记录了。）

### 16. ⚠️ `addJavascriptInterface` 是**按参数个数精确匹配**的

自定义源页要跟 Java 说话，桥方法里既有 0 参的（`ready()` / `lanStart()` / `clear()` / `back()`），
也有 1 参、2 参的。页面侧顺手写了个「统一补参数」的转发函数：

```js
function bridge(fn, a, b) { return window.yspCustom[fn](a, b); }   // ❌ 全按 2 个参数调
```

结果：**0/1 参的方法全部失效**，抛 `Error: Method not found`（不是静默丢参数，是直接报错）。
表现极具迷惑性 —— 页面渲染得好好的，但**永远收不到源列表、永远不起播**，
因为那个 `catch(e){}` 把异常吞了。

正确写法是**按 `arguments.length` 分派**，并且失败要 `console.log` 出来（能进 logcat）：

```js
function bridge(fn) {
  var B = window.yspCustom;
  if (!B || typeof B[fn] !== 'function') return undefined;
  var n = arguments.length;
  if (n <= 1) return B[fn]();
  if (n === 2) return B[fn](arguments[1]);
  return B[fn](arguments[1], arguments[2]);
}
// 转发时不能用 bridge(fn, a, b) 包一层 —— 会把参数个数固定成 3
window.__yspUI.rpc = function () { return bridge.apply(null, arguments); };
```

### 17. ⚠️ 两处「按键被吞」的坑（都会表现成「按键没反应」）

**(a) `playFailed` 的确认键拦截必须让位于浮层。**
`dispatchKeyEvent` 顶部有一条「播放失败时，确认键 = 重试」的快捷路径。
它少写了一个 `!manageOpen`：只要 `playFailed` 为真（**点播流播完也会置真**），
用户再按「菜单」打开源管理，**确认键在浮层里就彻底失灵** —— 每次确认都被截走去重试。
实测直接干掉 6 项键盘用例。浮层开着时按键归浮层所有：

```java
if (playFailed && !manageOpen && (code == KEYCODE_DPAD_CENTER || …)) { retry(); return true; }
```

**(b) 「退出」不能用 `pidof` 判。**
`finish()` 之后 Activity 确实没了，但**进程会被系统缓存住**（带 WebView 的进程尤其赖着不走），
`pidof` 照样有值。用 `pidof === ''` 当断言会得到一个**永远失败**的假断言。
判「用户看得见的退出」应该看前台窗口（`dumpsys window mCurrentFocus`）归不归我们。

顺带一条同类的：**返回键是分层退的**（键盘 → 菜单 → 面板 → 才轮到 Activity），
所以「连按两次退出」的测试要先把各层显式收干净，否则第一次返回只是收了个面板。

### 18. ⚠️ 播放器被 mediaserver 带坏之后，光 `stopPlayback()` 救不回来

**现象**：报错提示写着「按「确认」重试」，但**重试永远失败**，
`logcat` 里连刷 `地址无法交给播放器：java.lang.IllegalStateException`（还带不出堆栈，
因为只打了 `t.toString()`，而这异常没有 message）。

**根因**：mediaserver 挂掉后（`onError what=100 MEDIA_ERROR_SERVER_DIED`），
`VideoView.stopPlayback()` 内部是
`mMediaPlayer.reset(); mMediaPlayer.release(); mMediaPlayer = null;`
—— 而 `reset()` 在「服务已死」的播放器上会抛 `IllegalStateException`。
异常一抛，后面的 `release()` 和 `= null` **都不执行**，
VideoView 里就留下一个「既不释放又不可用」的 MediaPlayer，此后每次 `setVideoURI()` 都继续抛。

**解法**：把整个 `VideoView` 换掉（`rebuildVideo()`），让下一次 `setVideoURI` 从零 new 一个。
换的时候注意**插回原来的位置**（它是 SurfaceView，必须留在最底层，否则会盖住上面的透明面板）。
实测效果：重试从「连续 5 次全抛 ISE」变成「每次都能真正重新起播」。

```java
if (playerDead) rebuildVideo();   // play() 开头
```

另外**异常一定要带堆栈**（`Log.w(TAG, msg, t)`）。这里就是靠补上堆栈才确认了抛出点的。

### 20. ⚠️ 分组 tab 一多，选中项会被裁到屏幕外（v1.2 修的）

**现象**：分组超过两三个之后，按左/右键切分组，tab 栏**看着像冻住了** ——
高亮永远停在「全部 / 央视频道」，可下面的列表内容确实变了。
用户完全不知道自己现在在第几组，只能靠台名反推。

**怎么发现的**：拿一份真实聚合清单（`cn_all.m3u8`，10 个分组）跑
`tools/iptv_realworld_test.mjs` 才暴露出来。自己造的用例只有 2~3 个分组，永远碰不到。

**根因**：tab 条幅只有面板那么宽（1080p 电视上是 **192px**），
而 10 个分组的内容宽是 **899px**。CSS 侧其实是做对了的 ——
`overflow-x: auto` + 隐藏滚动条 + `flex: 0 0 auto`，本来就设计成可横滚。
**但没有任何一处代码写过 `scrollLeft`**：`renderTabs()` 只重建子节点，
没有「把 `.on` 那个滚进可见区」这一步。于是条幅一直停在 0，后面的 tab 全被裁掉。

实测（面板展开态，`custom.js` 修复前）：

```
tab 条幅：11 个 tab，可视宽 192px，内容宽 899px
  [0] 可见 「全部」        [1] 可见 「央视频道」
  [2] 出界 「General」 …  [10] 出界 「影视频道」   x=808→899
按右键逐个切组：每一组 scrollLeft 都恒为 0
```

**修法**（`custom.js` 的 `scrollTabIntoView()`，在 `renderTabs()` 末尾调用）：

```js
var max = elTabs.scrollWidth - elTabs.clientWidth;
if (max <= 0) return;                       // 排得下就别动
var tr = elTabs.getBoundingClientRect();
var or = on.getBoundingClientRect();
var delta = (or.left + or.width / 2) - (tr.left + tr.width / 2);
elTabs.scrollLeft = Math.max(0, Math.min(elTabs.scrollLeft + delta, max));
```

刻意**不用 `scrollIntoView()`**：它会把**所有可滚动祖先**一起滚（包括页面本身），
在 TV 上表现为整块画面乱跳。这里只动这一个条幅的 `scrollLeft`，影响面最小。

**顺带修的第二个**：面板收起时（整个列表+tab 都在屏外）按左/右键会**静默换分组**——
什么都没显示，用户只会觉得按键坏了。现在 `LEFT/RIGHT` 会先 `ensurePanel()` 把面板带出来，
和删除模式里已有的做法一致。

> 这条也有自动化守卫：`iptv_realworld_test.mjs` 会打开面板，
> **逐个分组切过去**，每一组都断言「选中的 tab 落在面板可见 x 区间内」、
> 且「tab 文字 == `currentGroup()`」，最后还要切回第 0 组确认 `scrollLeft` 能回到 0。

### 21. ⚠️ 「从网址导入」：判断规则、抓取层的取舍、以及它**不是**同步

v1.3 加的功能：给 App 一个清单网址，它自己去抓。看着简单，几个决定都值得记下来。

**① 为什么抓取放在 Android 侧，而不是局域网页面里 `fetch()`**

页面是电视自己吐出来的 `http://192.168.x.x:port/`，它去 `fetch('https://raw.githubusercontent.com/…')`
会被浏览器的同源策略直接拦掉（没有 CORS 头）。放 Android 侧就没有这个限制，而且
**抓完能把「清单地址」记下来**，下次一键刷新 —— 这才是聚合清单本来的用法。

**② 判定规则只有一处：`M3uParser.looksLikeChannelList()`**

一个 http(s) URL 到底是「频道清单」还是「一路直播流」，**光看地址分不出来**
（两者常常都以 `.m3u8` 结尾）。所以只能先抓、再看内容：

```
HTML（<html>/<head>/<!doctype>）        → 不是清单
单个流自己的清单（#EXT-X-TARGETDURATION / -STREAM-INF / -MEDIA-SEQUENCE）→ 不是清单
解析出 ≥2 条                            → 是清单
只解析出 1 条，但正文里有 #EXTM3U        → 也是清单
```

判错的两种后果都实在：把单个流清单当频道表 → 导入几十条指向 `.ts` 分片的**假频道**；
把频道表当单个流 → 用户以为导成功了，其实只有 1 条。
所以这段规则被 `M3uParserTest` 用各种形态钉住了（t25/t26）。

**③ `PlaylistFetcher` 刻意零 Android 依赖 —— 它和 `M3uParser` 一起在宿主 JVM 上单测**

因为它只用了 JDK 的东西（`HttpURLConnection` / `Charset` / `GZIPInputStream`），
所以可以**连 Android 一起绕开**：`tools/hosttest/PlaylistFetcherTest.java` 在 `127.0.0.1`
上起一个 HTTP 桩服务，把真网址永远测不到的支路全打一遍 ——

| 用例 | 为什么必须有 |
|---|---|
| 302 + **相对** `Location` | 默认实现不跟 `http→https`，也不给跳转链，所以自己跟 |
| 跳转成环 | 上限 5 跳，别被卡死 |
| GBK 清单（**而且服务器不声明 charset**） | 中文清单有相当一部分是 GBK，按 UTF-8 硬解就是满屏乱码 |
| UTF-8 BOM | BOM 不剥掉的话首行不是 `#EXTM3U`，解析器认不出来 |
| gzip 正文 | 请求头写了 `identity`，服务器照样可能发 gzip → 靠**魔数嗅探**兜底 |
| 404 / 403 / 超大正文 / 读超时 / 空正文 | 失败路径都要给出人看得懂的原因 |

> 静态检查里还有一条护栏：`PlaylistFetcher` **不许出现 `import android.`** ——
> 一旦有人往里加一句 `Log.d`，宿主单测就编不过。这是刻意留的。

**④ 「抓不到也照收」是故意的**

抓取失败（断网 / 403 / 超时）时，仍然把这个地址当成一条源收下，只是提示里说明原因。
理由：有些源就是要特定请求头、或者只在播放器里才拉得起来 —— **抓取失败 ≠ 播不了**。
顺带也保证了 1.2 之前「加一条直播地址」的行为没变。

**⑤ `importUrl` 是「顺带抓一下」，所以超时给得更短**

屏上键盘那条路上，用户按完「保存」就停在原地等。默认 8s 连接 + 15s 读最坏要 23 秒静默，
太长；改成 6s + 12s（`SourceImport.PROBE_*`）。公网清单绰绰有余 ——
43 KB 的 `cn_all.m3u8` 实测是 0.4 秒级。

**⑥ ⚠️ 「刷新远程清单」是合并去重，不是同步**

这一点必须说清，免得用户以为按一下就能跟上游对齐：App 里**没有「这条源是从哪份清单来的」
这个概念**，所以做不到「把上次这份清单带来的、这次已经不在清单里的条目删掉」。
硬要做就得给 `Source` 加来源字段、改存储格式 —— 那是另一件事（见「已知限制·下一步」）。
真要清干净就是「清空全部源 → 再刷新」，两下的事。

**⑦ 由此引出的两个细节**

- **「清空全部源」故意不删清单地址**（`SourceStore.clear()` 里只 `remove(K_LIST)` 和
  `remove(K_CUR)`）。地址不是「源」，而是「怎么把源弄回来」；留着它，「清空 → 刷新」
  这条路才走得通。不然用户就得对着电视重新敲一遍那一长串网址。
- **`reload()` 里必须顺带 `pushRemote()`**。会改到清单地址的路径不止一条
  （手机上的局域网导入、电视上的刷新），页面上那个「刷新远程清单」菜单项要跟着变；
  漏了这句，用户在手机导入完回到电视，菜单里那一项要等下次进页面才出现。
  （`setRemote` 在页面侧是幂等的，重复推没有代价。）

### 22. ⚠️ 「源管理」菜单一长，高亮行会被裁到卡片外（v1.3 修的）

和 §20 是**同一类问题、同一种修法**，区别只在方向（那边是横向 tab，这边是纵向菜单）。

「源管理」卡片高度封顶 84vh（`.mg-card` 的 `max-height`），而头部要显示两块信息
（局域网地址 + 已记住的清单地址，各两行）。结果在 1080p 电视上 `.mg-list` 只剩
**191px**，而 8 个菜单项要 **360px**。`.mg-list` 虽然写了 `overflow-y:auto`，
但**没有任何代码去滚它**：

> 光标走过第 4 项之后，高亮那行落在卡片外面 —— 按键照样有反应（状态在变），
> 用户却看不见自己在哪一项，只能凭感觉数。

实测数据（修复前，TV 1080p / WebView 视口 960×540）：

| 量 | 值 |
|---|---|
| 卡片 | top 42，高 456（正好顶到 84vh 上限） |
| 列表 | top 269，可见高 **191**，内容高 **372** |
| 可见项 | 只有前 3~4 项；**删除源 / 恢复示例 / 清空 / 关闭 全在卡片外** |

**修法**：`custom.js` 的 `scrollMenuIntoView()`，在 `buildMenu()` 末尾调用。
只做**最小滚动**（越界多少滚多少，不把选中项对到正中 —— 菜单上下键来回按时，
整块内容跳来跳去比看不见更难受）。顺带把头部两条提示各压成一行，
列表可见高度从 191px 提到 ~230px。

> ⚠️ 这条是**从截图上肉眼看出来的**，不是测试报的。原来的断言全在
> 「菜单项在不在、下标对不对」这一层，「在不在屏幕里」根本没人问 ——
> 这正是「跑绿了不等于没毛病」的一个实例。
> 现在 `custom_source_test.mjs` 里加了守卫：光标逐项走一遍，每一项都断言
> 「高亮行落在 `.mg-list` 的可见区内」（和 §20 里「每个分组的 tab 都要在可见区」
> 是同一个套路）。
>
> 另外要知道：**加这一项之前其实已经临界**（7 项要 327px > 191px），只是裁剪量小到
> 容易被当成「本来就这样」。多加一项只是把它推到了肉眼可见。
> 屏上键盘**没有这个问题**（实测 5 行键位都在卡片内，因为键盘的头部只有两个输入栏）。


### 23. ⚠️ 「只写了调用、忘了写定义」—— 前面全绿也照样是坏的（v1.3 修的）

这条和第 21、22 节不一样：它不是画面问题，是**验证方法本身的漏洞**。

写「从网址导入」时，导入页的 `post()` 收尾是这样的：

```js
.then(function () { btn.disabled = false; syncButtons(); });   // ← syncButtons 从没被定义过
```

`syncButtons` 这个名字只出现在**调用点**，文件里没有 `function syncButtons`。
于是 `loadList() → showRemote() → syncButtons()` 在页面加载时第一次就抛 `ReferenceError`。

**为什么所有断言都没拦住它：**

| 那层断言 | 为什么不拦 |
|---|---|
| `/api/addurl`、`/api/refresh` 的返回体、条数、分组名 | 全部是**直接 `fetch`** 打的，页面脚本一行都没执行 |
| 静态检查（路由在不在、字段在不在、有没有外部资源） | 只做文本匹配，「调用了但没定义」不在它的视野里 |
| `node --check` 语法检查 | 语法完全合法 —— 这不是语法错，是运行时的名字解析 |
| 设备端把按键走一遍 | 这条路径只有手机浏览器点得到，电视遥控器碰不到 |

而且它**没有任何外部症状**：不弹窗、不写日志、不崩 —— 抛在 Promise 链里，
只有打开控制台才看得到一行 `syncButtons is not defined`。用户视角是
「点了按钮好像没反应 / 按钮灰着点不动」，属于最难回报、也最容易当成玄学的那类。

**修法**（三处一起才好）：

1. 补上 `function syncButtons()`；
2. 把「记住的清单地址」提成模块级 `var remote`，按钮的可用性**只由它决定** ——
   不能由「这次请求结束了」决定，否则在没记住任何地址的机器上会留下一个可点的死按钮；
3. `#rre` 在 HTML 里默认 `disabled`，由 `syncButtons()` 打开。

**加的两道守卫**（这类错误要的是「让它自己浮出来」，不是再写一条文本匹配）：

* **静态**：扫 `lan_import.html` 里所有 `sync*/refresh*/update*/render*/show*` 开头的
  调用名，每个都必须在同一个文件里找得到定义（`function X` 或 `var X =`）。
  这次它报的是「检查了 2 个」—— 范围故意收窄，只盯「本文件内的内部函数」这类
  最容易漏的命名习惯，避免把 `document.getElementById` 之类误判进来。
* **运行时**：用 Playwright 真开一次导入页，`page.on('pageerror')` 收集未捕获异常，
  断言必须是 **0 个**；并在页面上真点一次「重新导入上次的」，把 `post()` 那条收尾路径
  也走一遍（此时记住的是本机桩服务的地址，刷新快、且合并去重后条数不该变）。

> 一句话教训：**覆盖了 API ≠ 覆盖了 UI。** 越靠近用户的那一层（页面脚本、按钮状态、
> 焦点可见性），越不能靠「直接调后端接口」来证明它没坏 —— 必须真的把它跑起来。
> 这一条和 §22 是同一枚硬币的两面：§22 是「画面对了但没人量」，这里是「接口对了但没人点」。

> 顺带修了构建脚本的一个同类问题：`build.sh` 以前**不 clean**，依赖 Gradle 增量。
> 踩过一次 —— 改完 `assets/custom.js` 后连跑 debug + release，**release 是新的、debug 是旧的**
> （`mergeDebugAssets` 认了缓存），而设备端套件装的正是 debug 包，于是整轮回归等于
> 跑在一个不含本次修改的包上，**「全绿」这件事本身不成立**。
> 现在 `build.sh` 一律先 `clean`（工程总共几十个源文件，clean 后也就几秒），
> 并且 debug 包也一并落到 `dist/`，免得再出现「dist 里那个 debug 是旧的」。


### 24. ⚠️ 修好「光标可见」之后，菜单**看上去**still 少了半截（v1.3 修的）

§22 修的是「光标跑到卡片外」—— 那是**功能**问题。修完之后再截图一看，还是不对：

```
局域网导入        已开启
屏上输入新源      直播流 / 清单网址
刷新远程清单      重抓并合并
选台播放          共 185 条 · 展开源列表       ← 半行
删除源 / 恢复示例 / 清空 / 关闭  ← 不在图上，而且没有任何提示说它们还在
```

`.mg-list` 的滚动条是**关掉的**（`scrollbar-width:none` + `::-webkit-scrollbar{width:0}`，
电视上不该出现滚动条），所以「下面还有 4 项」这件事在界面上**一点迹象都没有**。
用户（包括我自己看这张截图）的第一反应是「菜单怎么就 4 项」。

**修法要同时解决两件事，缺一不可：**

1. **一条文字提示**：`custom.js` 的 `updateMenuMore()` 算出可见区上下各有几项被裁掉，
   写成 `▲ 上面还有 N 项 ▼ 下面还有 N 项` 放在列表底部的 `.mg-more` 里。
   数字是**数出来的**，不是写死的；测试也按「提示里的数字 == 该方向被裁掉的项数」来断言。
2. **一道边缘淡出**：列表底部经常停着「半行」（§9 那条「行高凑整行」管的是**滚动对齐**，
   管不了列表可见高度不是行高整数倍这件事）。用 `mask-image` 把那一截抹掉
   （`.mg-list.cut-top / cut-bot / cut-both` 三种组合），比一刀切的边框干净。
   **用 mask 而不是 padding，是因为 mask 不动布局** —— 原因见下。

**这里踩了一个必须写下来的坑：提示条自己会引发「布局回环」。**

```
滚到光标 → 提示条出现 → 提示条占掉一行高度 → 列表变矮
        → 刚对准到下边缘的那一行又被顶出去 → 下一步再滚 → 提示条又变
```

症状很有欺骗性：**「光标在可见区」这条守卫开始红，红的是第 4~7 项；
同时「提示条说的条数」和「实际被裁的条数」差 1**。
（差 1 就是铁证：提示条是在「它自己出现之前」的布局上数出来的。）

**修法两件事一起做：**

* `scrollMenuIntoView()` 走**两遍**：第一遍滚 → 决定提示条出不出来 → 第二遍按最终高度再滚一次。
  提示条的显隐只会因为「放不放得下」翻转，第二遍之后必然稳定，不会来回抖。
  （注释写在函数头，别把 `for (var pass = 0; pass < 2; pass++)` 当成冗余删掉。）
* 边缘淡出用 `mask` / `class` 切换，**不用 padding** —— 不引入任何布局变化，
  从根上不参与这个回环。

> 教训：**「修一个显示缺陷」和「加一个提示」都可能改变布局，而布局一变，
> 上一条修复就可能失效。** 凡是「根据测量结果去改显示」的代码，
> 都要先问一句：这个改动会不会反过来改变我刚测量的东西？


### 25. ⚠️ 镜像自动顺延：归一化合错会「点 A 播出 B」（v1.4 加的）

**问题**：真实聚合清单里同一个台常有好几路地址，而这类清单**约 1/3 是死链**。
在这份 `cn_all.m3u8` 上量过：181 条里 **62 个台、43 个是多路的**，
宿主侧探活有 **35 条不通**。旧行为是「每一路都是独立的一行」，用户点进去是黑的，
得自己往下换一条、再等一次 15 秒看门狗 —— 一个台全不通就要手动试五六次。

**做法**：失败时自动试同一个台的下一路。归一化与选路全在 `Mirrors.java`
（纯逻辑、零 Android 依赖，和 `Source`/`M3uParser` 一起在宿主 JVM 上跑单测），
`CustomActivity` 只管「什么时候试、怎么提示、什么时候收手」。

#### 归一化：不做这一步，功能只能做一半

真实清单里明明是同一个台，写法却五花八门。**按严格同名分组 vs 按本类归一化分组**：

| 指标 | 严格同名 | 归一化 |
|---|---|---|
| 台名数 | 84 | **62** |
| 有镜像可退的台 | 47 | 43 |
| 覆盖条目 | 144（79.6%） | **162（89.5%）** |

规则（顺序即执行顺序）：**① NFKC**（全角→半角）→ **② 转小写** →
**③ 抹分隔符**（空白 `- _ · ． . 、 , ， : ： | / \ ~` + 零宽字符）→
**④ 剥尾部画质标签**（最多剥 3 轮：`(720p)` `(1080p)` `HD` `高清` `蓝光` …）。

实测的合并样本：`CCTV1`/`CCTV-1`/`CCTV-1 (720p)` → 6 路；
`CCTV-14`+`CCTV14` → 8 路；`湖南卫视`+`湖南卫视高清` → 2 路。

**⚠️ 两个必须记住的点：**

1. **第 ③ 步必须保留 `+` 和 `&`。** `CCTV5` 和 `CCTV5+` 是两个**不同的台**
   （真实清单里各 4 路）。顺手把 `+` 抹掉就会把两个台并成一个，
   选路时把用户从「体育频道」拽到「体育赛事频道」。
   所以分隔符表是**白名单式一颗颗列出来的**，不是「非字母数字全抹」。
   `MirrorsTest` 里有一条专门钉这个的用例，静态检查也查了 `SEPARATORS` 里没有 `+`/`&`。
2. **② 必须显式给 `Locale.ROOT`。** 用默认 locale 的话，土耳其语环境里
   `"I".toLowerCase()` 得到的是无点 `ı`（`i` 的另一种写法），CCTV 系列会全部对不上。
   这不是理论问题，是 JDK 有文档的行为，单测里有一条真的把默认 locale 切成 `tr-TR` 来验。

#### ⚠️ 没有台名的源**不参与**镜像分组

用户直接粘一个地址进来（屏上键盘 / 局域网页面填网址）时 `Source.name` 是 `null`，
列表里显示的是从 URL 截出来的兜底名。这种源要是也参与分组，
**所有匿名源会因为 key 都是 `""` 而被当成同一个台**，选路时把互不相干的地址
当成了彼此的镜像 —— 这是本功能可能犯的最坏的错（用户点 A 却播出了 B）。

所以 `Mirrors.key()` 对空名字一律返回 `""`，`count()`/`next()` 见到 `""` 直接放弃。

> 这条同时也是 §18 那个「播放器有没有被毒死」守卫成立的前提：那条人为死链
> 就是**匿名源**（`POST /api/add` 裸地址）。它要是也能顺延，就会跳到某个同名台上去，
> 「换回可用源还能播」就不再是在验证播放器了。
> `iptv_realworld_test` 里有一条断言专门钉这一点。

#### 收手条件，以及三个反直觉的坑

收手有两个条件（任一满足即停）：试满 `Mirrors.MAX_ATTEMPTS = 4` 路，
或整轮超过 `Mirrors.WALK_BUDGET_MS = 40s`。

**参数是量出来的，不是拍的**（宿主侧探活 162 个有镜像的地址）：

| 类别 | p50 | p90 | max |
|---|---|---|---|
| 活链（取清单） | **108 ms** | 619 ms | 2,698 ms |
| 死链 | **5,002 ms** | 5,003 ms | 6,003 ms |

死链的主流失败方式是 `UND_ERR_SOCKET` 在 **5.0 秒整**（28/35）——
连接被黑洞吞掉后干等，不是快速拒绝；另外 5 条 404、1 条证书过期是秒失败。
也就是说**单次尝试的真实成本约 5 秒**，按 4 路算是 ~20 秒；
只有每一路都撞上 15 秒起播看门狗才会到 45 秒，那正是 40 秒预算存在的理由。

**坑 ①：试过的记录不能在「起播成功」时清空 —— 会造成镜像之间来回弹。**
清掉之后会出现 `A 起播→失败→B 起播→失败→A…` 的循环
（每次成功都把刹车松开，而 `MAX_ATTEMPTS` 数的是「试过几条」，
清空就让这个计数永远涨不上去）。所以 `mirrorTried` **只在**
「用户主动选 / 换到别的台」时清。静态检查里有一条断言禁止在 `onPrepared` 里清它。

**坑 ②：但时间预算必须在「起播成功」时重置。**
不重置的话：一条流正常播了十分钟之后断掉 —— 那时预算早就过期，
镜像顺延会**静默失效**、直接报「无法播放」。
功能等于只在开播后 40 秒内活着。这条也有静态断言钉住。

**坑 ③：推进必须延迟出去（250ms），不能在 `onError` 回调里直接 `play()`。**
`failWith()` 可能是从 MediaPlayer 的 `onError` 里进来的，
在回调里立刻 `stopPlayback()` + `setVideoURI()` 是重入。
同时用 `playGen` 世代号核对：用户在失败后 250ms 内自己选了另一条源，
这个延迟任务必须作废，否则会把用户刚选的台又拽回去。

**顺带一提**：用户打开「源管理」浮层时**不顺延** —— 那是「我要接管」的信号。
点播播完（`onCompletion`）也不顺延 —— 那是正常播完，不是失败，
接上去会导致「看完一集自动去试别的台」。两条都有静态断言。

#### 为什么**没有**做「每行显示 ×N 镜像数」

想过，放弃了。181 条里 162 条都属于有镜像的台，逐行打角标是纯噪声，
而且会动到 §22/§24 刚调好的行布局（`labels()` 走的是 `innerText`，
角标只能用伪元素画才不会污染它 —— 而 `::after` 已经被 ✕/⚠ 占着了）。
改成把信息放在**用户真正会看的两处**：
顺延过程中的状态层（「这个台的第 2/4 路地址…」+ 「这一路不通，自动换同一个台的下一路」
+ 「按『菜单』键可以直接换别的台」），以及顺延成功后的提示气泡
（「这一路不通，已自动换到「CCTV-1」的第 2 路地址」）。

顺延时**每一路失败都会推给页面**（`playFailed(url)`），所以死掉的地址会在列表里
逐个变暗并打上 ⚠ —— 用户回头扫一眼就知道哪些是死的，
这些标记也是下一轮顺延的排序依据（未失败的优先）。

### 26. 体积：图标那 22% 是怎么砍下来的（minSdk 21 之后的第二次反转）

#### 1.4 那一轮（minSdk 19）

1.4 首轮的 release 包是 **124,461 字节**，压缩后构成是：

| 部分 | 压缩后 | 占比 |
|---|---|---|
| `classes.dex` | 41,878 | 33.6% |
| `assets/`（6 个文本文件） | 36,028 | 28.9% |
| `res/*.png`（图标与横幅） | **27,912** | 22.4% |
| 其余（manifest / arsc / xml / 签名） | 18,643 | 15.0% |

一眼看去最怪的是 PNG：**12 个 PNG，全部是 STORED，一个字节都没压缩**。
而且源码里只有 **7 个** PNG —— 多出来的 5 个是 AAPT2 生成的。

根因：`minSdk 19`，而 AAPT2 在 `minSdk < 21` 时会把每个 **VectorDrawable 烘成一整套
各密度的 PNG** 塞进包里。项目里正好有两个矢量图（`drawable/ic_launcher.xml` 和
`tv_banner.xml`），于是多出 `81×81`、`240×135`、以及一个 **`1280×720` 的横幅（8,534 字节，
本地根本没有这么大的图）**。

四种做法都实测过（release 包真实字节数，不是估的）：

| 做法 | 包大小 | 说明 |
|---|---|---|
| 手写位图 + 两个矢量图（改之前） | 124,461 | AAPT2 补烘 3 档 PNG，共 27,912 |
| **删掉位图、只留矢量图** | **135,531** | **反而更大**——烘出来 12 档，且比手写的大（432²：手写 4,115 vs 烘出 5,792） |
| 矢量图挪进 `drawable-anydpi-v21` | 124,577 | 没用，照样烘全套 |
| 只留手写位图（横幅尺寸还带着旧 bug） | 107,690 | PNG 降到 7 个 13,689 |
| 只留手写位图 + 修好横幅尺寸（1.4 最终） | **115,715** | 9 个 PNG，横幅补到 4 档且尺寸正确 |

当时的结论是「**不要再引入 VectorDrawable**」—— 在 minSdk 19 的前提下，这个结论是对的。

#### 1.5 这一轮（minSdk 21）—— 结论整个反过来

放弃 Android 4.4 之后 `minSdk` 提到 21，**AAPT2 不再烘 PNG**，于是上面那条结论失效，
矢量图从「最差选择」变成「最优选择」：

| 做法 | 包大小 | 说明 |
|---|---|---|
| 1.4 最终（位图图标 + 位图横幅，minSdk 19） | 115,715 | 9 个 PNG 共 27,912 |
| 1.5 中间态（minSdk 21，图标仍是位图） | 115,304 | 只删了 Api21 与低版本守卫，-0.4% |
| **1.5 最终（minSdk 21 + 矢量图标 + 位图横幅）** | **104,231** | **PNG 只剩 4 张横幅，共 10,633（-61.9%）** |
| 1.5.1（面板顶部「自定义源」入口的 CSS+JS） | 107,618 | +3,387，功能成本 |
| **1.6（minSdk 24 + 删掉内核能力体检）** | **102,878** | **比 1.5 还小 1,353；debug 122,013** |

1.5 release 的构成：

| 部分 | 压缩后 | 占比 |
|---|---|---|
| `classes.dex` | 41,581 | 42.6% |
| `assets/`（6 个文本文件） | 36,028 | 36.9% |
| `res/`（4 张横幅 PNG + 4 个 XML） | **12,533** | 12.8% |
| 其余（manifest / arsc / 签名） | 7,536 | 7.7% |

其中矢量图标 `res/r2.xml` 压缩后只有 **429 字节**，顶掉了原来 mdpi~xxxhdpi 五档位图
（合计约 17,000 字节）。debug 包同步从 139,869 降到 **123,165（-11.9%）**。

**现在的纪律（已写进 `build.gradle` 的 minSdk 注释）**：
- 桌面图标 **用矢量**（`drawable/ic_launcher.xml`，由 `tools/gen_icons.py` 生成）；
- 电视横幅 **仍是位图** —— 它是 Android TV 主屏的门面，各家 launcher 怎么取不一定
  （有的按位图解码），矢量在这里赌不起；
- 两条都配了断言，且断言钉的是「**是矢量**」**且**「**确实没被烘成 PNG**」——
  只写前一条的话，哪天 minSdk 被改回 19，包会悄悄胖回去而断言仍然绿。

**顺带修掉一个真 bug**：横幅原来只有 xhdpi/xxhdpi 两档，而且**尺寸算错了** ——
设计空间是 320dp×180dp，按密度换算 xhdpi(2x) 应该是 `640×360`、xxhdpi(3x) 是 `960×540`，
但 `gen_icons.py` 生成的是 `320×180` / `480×270`（只有标准的一半），却放进 xhdpi/xxhdpi 目录。
等于告诉系统「这是一张 160dp 宽的图」，在 xhdpi 电视上被放大两倍 —— **横幅白白变糊**。
现在补成 mdpi/hdpi/xhdpi/xxhdpi 四档正确尺寸（**刻意不出 xxxhdpi**：1280×720 那张要
11,936 字节，而真报告 xxxhdpi 的电视极少，4K 电视按 density 分类多数仍落在 xhdpi/xxhdpi，
到 xxhdpi 已覆盖 720p~4K，剩下的由系统放大 1.33 倍，纯色块看不出来）。
这两条都写成了断言，1.6 之前在 `legacy_capability_test.mjs`，
现在由 `custom_source_test.mjs` 的静态段接管。

**没做的两项（理由）**：
- **压缩 `assets/`**：注释占 22%（约 17.5K 未压缩），但压缩后只省 ~5K（4%），
  而 minify JS/CSS 有改坏语义的实际风险，还会破坏「APK 里 6 个 assets 与源码逐字节一致」
  这条构建校验。收益不划算。
- **开 `minifyEnabled`**：零第三方依赖，能省的未使用代码本来就少，主要靠缩短标识符，
  约 4~6%。但 `addJavascriptInterface` 暴露给 JS 的方法名**不能被重命名**，
  一旦 keep 规则写漏，`custom.js` 调 `yspCustom.xxx()` 就会静默失效 ——
  这是拿核心功能换 5% 体积，不值。真要开，先补 `-keepclassmembers` 再全量回归。

### 27. 一轮代码审查抓到的 6 个真 bug（1.4 已修）

测试全绿不等于没 bug。这一轮把 13 个 Java 文件逐个过了一遍，修掉 6 个，
其中 **1 号是最讽刺的一个**：

**① 镜像顺延在「开播 40 秒后」永久失效（功能失效·静默）**
`WALK_BUDGET_MS` 是 40 秒的整轮预算，但预算起点被写在了 `onPrepared`（起播成功那一刻）。
于是真实场景是：用户看满十分钟 → 流断了 → `now - mirrorWalkStart` 已经十几分钟 →
超预算 → **一路都不试，直接弹「无法播放」**。功能等于只在「一点就死」的场景里活着。
改：预算改从**这一串失败的第一次失败**起算（新增 `mirroring` 标记）。

> ⚠️ 值得单独记一笔：**当时有一条静态断言专门钉这个，而且它是绿的。**
> 断言写的是「`onPrepared` 里必须有 `mirrorWalkStart = now()`」——
> 它钉住了**实现细节**，却把**语义**钉反了，于是「断言全绿」和「功能是坏的」同时成立。
> 现在两条断言改成钉语义：起播成功时**不许**给预算重新计时，
> 且 `failWith` 里必须 `if (!mirroring)` 才起算。

| # | bug | 后果 |
|---|---|---|
| ② | `onPause`/`onDestroy` 不清 Handler 回调。起播看门狗（15s）和顺延任务都是 `postDelayed` 的 | 退出/切后台后任务照跑 → 顺延 → `video.start()`，**电视自己响**（无 Surface，有声无画），只能杀进程 |
| ③ | `onPause` 写成 `if (video.isPlaying()) video.pause()` | 缓冲中 `isPlaying()` 是 false，`pause()` 不被调用，而 `mTargetState` 只在 `pause()` 里才设成 PAUSED → **缓冲中切后台 = 后台自动播放** |
| ④ | `setVideoURI(Uri, Map)` 是 **API 21** 的方法，`minSdk` 却是 19 | 4.4 上带 Referer/UA 的源 100% `NoSuchMethodError`（IPTV 源带请求头是常态）。已加 `SDK_INT` 守卫退回无头版本 |
| ⑤ | `MainActivity` 那个「每 15 秒自我重排」的补注入任务，`if (pageReady)` 就永远续命，`onDestroy` 从不清它 | Activity 连同 WebView **永久泄漏**到进程被杀；销毁后还会 `Toast.makeText(已finish的Activity)` |
| ⑥ | `M3uParser` / `PlaylistFetcher` 共 10 处 `toUpperCase()`/`toLowerCase()` 没给 `Locale.ROOT` | 土耳其语 locale 下 `"#EXTINF"` 变成 `"#EXTİNF"`，**整份清单解析出 0 条**。`Mirrors` 里专门防了这个坑，解析层和抓取层漏了 |

> ① 的**端到端验证没做**：要验它得有一条「能稳定播 45 秒然后失败」的可控流，
> 造起来成本高，而且断流时机不可控会让用例变成抛硬币。
> 目前靠静态断言钉语义 + 代码审查保证，这条如实记着。

**审查后确认没问题的**：`Mirrors`（状态机走了一遍，4 路全失败会被 `withinCount` 拦停，
不会死循环；`fallback` 也会被收进 `tried`，不会绕回同一条）、`SourceStore`、`M3uParser`、`PlaylistFetcher`、
`SourceImport`、`TvShellActivity`；`LanImportServer` 也确认**没有**路径穿越/未授权读文件
（唯一读 assets 的是硬编码文件名，`/api/addurl` 只回 `ok/parsed/added` 不回显抓取内容，
`Content-Length > 4MB` 在读 body **之前**就拦了）。

**记进已知限制、这轮没修的**：进入「删除源」模式时 `custom.js` 会把 `manage` 置回 false，
于是「不在用户背后换台」那道守卫失效 —— 播着一条会失败的源时进删除模式，
App 会在你选删除目标的背后自己换台。修它要新增一个 JS→Java 的桥方法
（而 `addJavascriptInterface` 是按参数个数精确匹配的，见 §16），风险与收益不成比例，先记着。

> ⚠️ 前置：这个脚本**不自建环境** —— 需要手机模拟器在线、APK 已装、
> 且 `adb forward tcp:9223 localabstract:webview_devtools_remote_<pid>` 已建好
> （`device_test.mjs` 同理，它要 **9222**）。转发指向的 pid 过期时表现是

> ⚠️ **这个脚本对「手机」的要求是双重的**，缺一条就跑不了（1.5 这一轮两条都踩到了）：
>   ① **内核要够新** —— 它依赖注入进央视频页面的 `__yspTV`，
>      而页面本身要 MSE + WebAssembly。在 API 21（内核 Chrome/37）上页面根本渲染不出来，
>      于是「注入失败」，看上去像代码坏了，其实是环境。
>   ② **设备要被判成手机** —— 必须是 `SENSOR_LANDSCAPE` 分支。
>      有些模拟器（本轮那台 API 21）会被 `isTv()` 判成电视，走硬锁分支，
>      `phone_orientation_test.mjs` 的「左右翻转」三条就一定红。
> 所以要跑这两项，得是一台**内核够新、且被判为手机**的模拟器（本轮为此建了 API 36 的）。
>
> ⚠️ 坐标类点击要等**列表停稳**再取。面板一打开 inject.js 会把正在播放那一行滚进视野，

它分五段：

| 段 | 内容 |
|---|---|

| C2 镜像顺延 | **在真清单的真地址上**验一次镜像顺延：把某条「已经出过画」的地址的台名原样抄给一条必死地址，人为造出「同台第 1 路是死的」，断言真的跳到了同台的另一条真地址（v1.4 新增） |
| D 收尾 | 清空到**零源**（1.9 起没有示例源可恢复，「停在零源」本身就是一条断言），把测试设备收拾干净，并核对**每一段都真的跑到了** |

> ⚠️ C2 那一段的第三点（「每个章节都真的跑到了」）不是凑数的：这份脚本是顺序执行、
> 遇异常直接崩的，中途一个 `ReferenceError` 就会让进程当场退出 ——
> 前面已经打出来的 ✓ 全都留在屏幕上，而结尾的汇总行**根本不会打印**，
> 看上去就是「一大片绿」。C2 真发生过一次（引用了上一个块里的 `const`），
> 没有这张台账的话这一轮就会被当成通过。

实测结论：

- **导入没问题**：181 条 → 落库 180 条（清单里有 1 条重复地址，App 按 url 去重，这是对的）。
- **3000 条压力**：8 秒内导入完，落库 2000 条（`M3uParser.MAX_ITEMS` 截断），不卡不崩。
- **真播：这一轮 5/6**（多轮实测在 4/6 ~ 6/6 之间波动）。
  唯一稳定失败的是 `CCTV2 @ 120.198.95.220:9901`，**已定位到不是 App 的问题**：
  | 检查项 | 结果 |
  |---|---|
  | 宿主取它的清单 | **200**，是合法 HLS 媒体清单 |
  | 宿主取它的第一个分片 | **200**，`application/octet-stream`，开头 `47 10 11 1f`（TS 同步字节） |
  | **同一个 host:port** 上的 CCTV1 / CCTV3 | **设备上出画正常** |
  | 设备端 | 失败，重试一次仍失败；但其中有一轮重试就成功了 |
  → 地址和网络都是好的，同一段代码在同一个 host:port 的兄弟流上工作正常。
  结论：**模拟器的 framework MediaPlayer 对这条流偏脆**（9901 那批流连分片清单都带着
  `##EXT-X-VERSION:3` 这种不规范标签），不是 App 的控制流问题。记进「已知限制」。
- **死链之后播放器不会被带坏**：这一条查了两轮才站稳 ——
  以前回退目标是「宿主探活的第一条」，实测那条本身就该播不了，
  于是守卫假红（§见下面的两条经验）；现在回退到**本次一次就出画、而且是最新的一条**。
  另外手工复验过：播 A → 播死链 → 立刻回退 A，全程出画。
- **两条经验值得记住**：
  1. 这类清单里约 **1/3 是死链**（本轮 181 条里 59 条连不上：30 条 socket 失败、
     23 条超时、4 条 404、1 条 403、1 条证书过期）。所以「导入后一片台名」不等于「都能看」，
     界面上的 ⚠ 标记和第二路镜像就变得很实用（见「已知限制」）。
  2. 判死链**别用 `10.255.255.1` 这类黑洞地址做测试**：Linux 的 SYN 重传要一两分钟才放弃，
     虽然 App 有 15 秒起播看门狗兜底，但取样窗口一不小心就过了 —— 用例会变成抛硬币。
     改用设备本机的 `127.0.0.1:1`（立刻 ECONNREFUSED），判定才确定。

> 这个用例顺带抓出了一个真 bug（分组 tab 不跟随选中项），见 §20。

**v1.3 起，这份清单的地址本身就能当导入目标**：`custom_source_test.mjs` 的最后一段
会把它当普通清单网址喂给 `/api/addurl`，验证「抓取 → 判定 → 整份导入 → 记住地址」
这条完整链路（前面那些自己造的桩用例负责把边界分支跑满，这一段负责证明真地址也走得通）。

#### ⚠️ 提 minSdk 顺手带出来的一个坑：AGP 偷偷开了 multi-dex

`minSdk` 从 19 提到 21 之后，**AGP 默认把 `multiDexEnabled` 打开了**（5.0 起 ART 原生支持
多 dex，AGP 就自作主张分包）。产物从「单 `classes.dex` 98,460 B」变成
「`classes.dex` 2,972 + `classes2.dex` 95,704」。

我们总共十来个类、方法数离 65K 差得远，**根本不需要分包**，付的却是实打实的代价：

1. **首次安装后要多 dexopt 一个 dex，冷启动变慢。** 这一条是测试逼出来的：
   `phone_touch_test.mjs` 的两条**早期**用例（【1】轻点拨出面板、【4】点第 5 行选台）
   在 1.5 分包版上失败，后段的用例（【3】【5】【6】【7】【8】）全过 ——
   正是「早期落在页面还没稳的窗口里」的形状。
   同一台设备、同样的起始状态（`count=40 / playing=0 / CCTV1`）：
   **1.4（单 dex）22/22，1.5（分包）20/22**，把 multidex 关掉后 **1.5 恢复 22/22**。
2. **最低那批设备正好是 5.0/5.1（API 21/22）**，而 ART 在多 dex 上出过的类加载问题
   恰恰集中在 21~22 这两个版本上 —— 白白多一处风险。

修法是在 `defaultConfig` 里显式写 `multiDexEnabled false`（能成功关掉本身也反证了没超方法数）。
关掉后回到单 dex，dex 还比 1.4 更小（删掉 `Api21` 的效果）：
debug 97,764 B（1.4 是 98,460）、release 87,296 B。

> 教训：`minSdk` 这种「看起来只是改个数字」的改动，会连带改掉 AGP 的一批默认行为。
> 改完别只看编译过没过，**要看产物的实际构成**（dex 分包、资源编译方式都会变）。

#### ⚠️ 没删的（别顺手删，每一条都有具体理由）

| 项 | 为什么留着（**1.6 复核过，前两条依然成立**） |
|---|---|
| `Api28` / `Api30` 隔离类 | **隔离线跟着 minSdk 走，不跟着 compileSdk 走**。1.6 起最低那批是 7.0（API 24），而 24 < 28 < 30 —— 加载含 API 28/30 类型的类照样 `NoClassDefFoundError`。别说「都 7.0 了还隔什么离」 |
| 不重写 `onReceivedError(WebView, WebResourceRequest, ...)` | 那两个参数类型是 **API 23**，minSdk 24 ≥ 23，**技术上现在可以重写了**；但仍不写 —— 框架默认实现本来够用，重写等于抄一遍默认行为 |
| v1(JAR) 签名 | ~~v2 签名是 API 24 才有的~~ **1.6 起不再是硬要求**（minSdk 24 = 7.0 支持 v2）。默认仍会同时签 v1+v2，没动它 |
| ~~内核能力体检页~~ | **1.6 已删除**（minSdk 24 → 7.0 以下装不上，不需要解释为什么黑屏）。见 §15/§30 |
| 横幅 `tv_banner` 仍是位图 | Android TV 主屏的门面，各家 launcher 取法不一定（有的按位图解码），矢量赌不起 |

### §37 v1.13：换台手感再榨一轮 —— 一次换台的账到底花在哪

**用户反馈**：「在电视上用遥控器上下换台的时候，还是有点卡顿，反应慢。」

#### 先把账算清楚，再决定动哪里

从手指按下到看见新画面，一次换台的钱是这么花的：

| 段 | 耗时 | 归谁 | 能动吗 |
|---|---|---|---|
| 按键 → 气泡出新台名 | ~0ms | 我们 | 已经是最优 |
| 防抖窗口 | 250ms | 我们 | 见下 |
| 站点重新起流（卸旧源 → 挂新源 → 首帧） | **1.3–1.6s** | 站点自研 WASM 播放器 | **绕不开** |
| 气泡比画面早撤造成的空窗 | 最多 ~500ms | 我们 | **能，而且是体感大头** |

结论很硬：**站点那 1.3–1.6s 是大头，但只要还待在 WebView 外壳里就绕不开**
（那是 `hls.cmg.js` 自己的卸/挂序列）。这轮不碰它，只把「我们这段」和
「中间的体感」榨干。谁要再把这段砍下去，那就得离开 WebView 外壳 ——
自己抓流地址、用原生播放器播，属于另一个工程量级，也正好踩在
「这只是一个外壳、不绕任何鉴权」这条定位上。

#### ① 阀门提前解锁：排队不再傻等满 1500ms

老逻辑：车排队之后 `setTimeout(剩余阀门)`，到点才发。可站点自己只要
1.3–1.6s 就出画，阀门却压了 1.5s —— 用户一台一台正常往下翻时，
第二次按键经常要白等几百毫秒，这就是「反应慢」最直接的一处。

改成盯着站点播放器：`readyState>=3` 且在走、`networkState` 空闲、
`currentTime>0`、有画面尺寸 —— 四条同时满足就立刻发下一趟。

```js
var left = deadline - Date.now();
if (left <= 0 || (Date.now() - armedAt >= floor && playerSettled())) {
  unlockTimer = 0;
  fireSwitch(switchWant, true);      // 内部会清掉"到点发车"那个 timer，不会叠发
  return;
}
```

**两条保险**（这是唯一可能碰到 1.7 修过的「播放器被打死」的改动，不能省）：

- **硬下限** `floor = 60% × SWITCH_GAP_MS`（900ms）。就绪判得再快，两次碰站点
  播放器之间也至少隔这么久。复现死亡的连按间隔是 120ms，这里差 7 倍以上。
- **到点兜底** `left <= 0` 仍然照发。判不出就绪时行为与老逻辑**完全一致**，
  不会把「永远等不到出画」变成死等。

`cancelSwitch()` / `flushSwitch()` 也必须撤这个轮询 —— 否则「按回当前台」之后
一个迟到的换台会突然插进来。

#### ② 换台气泡守到出画再撤

老逻辑气泡 1.6s 就撤，而站点要 1.3–1.6s 才出画。于是有一段时间
**提示没了、画面还是上一台** —— 用户不会去分析"哦这是站点在起流"，
他读到的就是「卡住了」。这一条改的是**体感**，不动任何时序。

守到 `playerSettled()`（或最多 6s 兜底），再留 900ms 看清台名。

> ⚠️ `inject.js` 被自定义源页复用，而那一页**没有 `<video>`**（原生播放器）。
> 所以 `showToastHold()` 开头先探一眼：没有 video 就按普通气泡的 1.6s 节奏撤，
> 别白等 6 秒。逻辑级测试里专门有一条盯这个（`switch_logic_test.mjs` ⑧-b）。

#### ③ 一次按键只算一次 rows()

`move()` 收起态链路里 `rows()` 原先被问 **4 遍**：`move()` 自己、
`playingIndex()`、`labelAt()`、`paint(false)`。每遍都要对约 40 个可见行做
`getBoundingClientRect()` —— 那是**强制重排**，4 遍就是 4 次。弱一点的电视盒子上，
这就是「按键发涩」的直接来源。

改成算一遍传下去（`playingIndex(rs)` / `labelAt(target, rs)`）。
逻辑级测试直接数量：一次 `move()` 从 160 次量行降到 **40 次**。

#### ④ 收起态不再 `paint(false)`

面板收起时整个面板被 `translateX(-101%)` 挪在屏幕外，画光标**没有任何可见效果**，
却要 `clearFocus()` 扫 40 行 + `ensureEntry()` 查一次 DOM。开面板时
`openPanel()` 会 `paint(true)` 补上，所以收起态直接跳过。

#### ⑤ MainActivity 少绕一圈消息队列

`dispatchKeyEvent` 本来就跑在主线程，而 `js()` 里又 `ui.post(...)` 一圈才到
`evaluateJavascript`。改成主线程直接调，只有从 JS 桥线程这类非主线程路径进来
时才转投。

#### 专项套件

`tools/switch_logic_test.mjs`（**1.13 新增，14/14，不需要设备**）：
用一份极简 DOM 桩把 `inject.js` 真跑起来，盯的是**状态机**而不是像素 ——
单按一次 / 连按 5 次 / 提前解锁 / 兜底 / 按回当前台撤单 / `rows()` 次数 /
收起态不写 class / 气泡守屏。站点行为也仿真了：谁被 click，`tvSelect` 就挪到谁身上。

> ⚠️ 为什么值得为「不需要设备」单写一套：设备端套件要一台电视或模拟器，
> 而「改完立刻知道有没有把逻辑写坏」不该等设备。逻辑级挡住了，
> 真机就只需要去验手感和播放器死活这两件真设备才能回答的事。

### §36 v1.12：换台防抖 —— 为什么不是「等 1 秒」

**用户提议**：「上下换台不要立即切换，等待 1 秒这样就不会卡顿了。1 秒是不是太长了？」

#### 先量，别先改

`tools/switch_delay_probe.mjs` 扫不同延迟，量**「停下按键 → 画面出来」**的真实耗时：

| 固定延迟 | 停下按键 → 出画 |
|---|---|
| 0ms（现状） | 1383ms |
| 300ms | 1154ms |
| 600ms | 1694ms |
| **1000ms（提议）** | **1873ms** |

**1 秒确实太长。** 固定延迟把用户的等待又拉长了近半秒，而它想换来的好处
（连按 5 次只切 1 台而不是 5 台）用**防抖**能拿到，且不额外加延迟。

#### 改成了防抖（250ms）

| | 固定延迟 1 秒 | **防抖 250ms（采纳）** |
|---|---|---|
| 连按 5 次 | 切 1 次，但延迟 1 秒 | 切 1 次，延迟 0.25 秒 |
| 单按一次 | 延迟 1 秒 | 延迟 ~0.27 秒（实测） |
| 中间那几台 | 会被短暂切到 | **一次都不碰** |

关键差别在最后一行：卡顿的真正来源是**反复 detach/mount 站点那个
自研 WASM 播放器**，而防抖期间我们**一次都不去碰它**（实测 `playing` 原地不动）。

阀门（`fireSwitch` 的 1500ms）**保留** —— 它是 1.7 修「连按把播放器永久敲死」的，
管「多久能发一趟」；防抖管「按键停了才发」。两条机制不冲突，各管一件事。

#### 防抖踩到的一个真 bug：连按 5 次只走 1 格

`move()` 的续算基点原本只在 `switchWant >= 0`（阀门攒单）时才从「我们的意图」续，
但**防抖挂起期间 `switchWant` 一直是 -1**（车还没进阀门）——
于是每按一次都从滞后的 `playingIndex()` 重算，位移被吃掉 4 次。

```js
// 「意图」有两个来源，谁有值就从谁续
var intend = (switchWant >= 0) ? switchWant
           : (switchDebTimer && debWant >= 0) ? debWant
           : -1;
```

另外 `cancelSwitch()` 里必须 `clearDebounce()`，否则「按回当前台」之后
那个还挂着的防抖定时器会在 250ms 后照旧发车 —— 用户明明说了「不换」。

#### 专项套件

`tools/switch_debounce_test.mjs`（**6/6**）从干净起点验四件事：
连按 5 次光标跟到底 / **按键期间站点一次都没被惊动** / 停手后落到最后一台 /
单按延迟≈窗口 / 按回当前台不换。

> ⚠️ 写这个套件时踩到两个坑（都是**站点行为**，不是被测代码）：
> ① `adb input keyevent` 在起播后**只有第一按被收到** —— 站点的 WASM 播放器
> 抢走了键盘焦点，看起来像「防抖吞了按键」。改走 `__yspTV.move(d)` 直调
> （`MainActivity` 那边本来就是 `keyevent → move(d)`）。
> ② 原节流套件跑到后面光标已被推到二十几台，「光标在第 0 台附近」这个起点假设失效，
> 那些断言测的是别的位置 → 把「停手才换台」「按回当前台撤单」两组移出，
> 改由这个新套件从干净起点覆盖。

### §35 v1.11：订阅源的同步删除与退订

**用户反馈**：「订阅源的删除，现在是只能添加。有些失效的订阅源不能处理」。

#### 为什么原来做不到

App 只知道「现在有这些条目」，**不知道「哪些是这份清单带来的、哪些是我自己加的」**。
合并式刷新（只增不减）就是被这个信息缺失逼出来的 —— 源码里那段注释写得很直白：
「App 里没有『这条源是从哪份清单来的』这个概念，所以做不到……」。

#### 修法

| 改动 | 说明 |
|---|---|
| `Source` 加 `from` 字段（存储键 `"f"`） | 记录这一条来自哪份清单 —— **整个功能的地基** |
| 「刷新远程清单」→ **「同步这份清单」** | 语义从只增不减 → 按上游现状同步。上游下架/改名的台会被删掉 |
| 菜单新增 **「退订这份清单」** | 删掉它带来的全部源 + **连地址一起清掉** |
| 正在播的那条被删了 → 自动换台 | 否则播放器会一直抱着一条已不存在的源 |

「退订」为什么**连地址一起清**、而「清空全部源」**刻意保留**地址：
前者是「我不要这份了」（留着地址还能一键拉回来就不叫退订），后者是
「我清一下等会儿再拉回来」（清掉地址就得对着电视重打一遍几十字的网址）。

#### ⚠️ 最要紧的边界（也是最贵的错）

**只删 `from == 这份清单` 的**。三种一律不碰：
① 自己手加的（`from` 为 null）；② 来自**别的**清单的；③ 上游改名后地址变了的那条旧记录
（那是「删一条+加一条」，不是重复）。

越界一次就是误删用户的真台，而这行代码删起来毫不显眼 ——
所以专门写了 `tools/hosttest/SourceSyncTest.java`（**24 条**）守住它，
并配了一条静态断言直接盯 `s.fromList(listUrl) && !inList.contains(s.url)` 这行。

**1.10 及以前导入的条目没有 `from` → 第一次同步不删任何东西**（它们看起来像手加的）。
这是有意的保守：宁可先不删，也不能把用户 172 条真台当垃圾清掉。
但会**就地补上 `from` 标记**，所以从第二次同步起就正常工作了。

#### 单测抓到的一个真 bug

把核心逻辑抽成纯函数 `planSync(cur, parsed, listUrl, curPlaying)`
（不碰 Context/SharedPreferences，遵循本项目「零 Android 依赖才好单测」的既有约定）。

单测立刻抓出：**`listUrl` 为空时 `kept` 留空就 return** ——
返回的 `kept` 和实际存储不一致。设备上侥幸没出事
（`syncFrom` 靠 `!kept.isEmpty()` 跳过了 `save`），但这是**「靠下游兜底才不出错」的写法**，
早晚会出事，而且一次误判就是清空用户列表。已改成「空地址 → 原样返回 `cur`」。

> 配套：`tools/hosttest/stub/` 补了 `android.content` / `android.util` 的最小桩
> （方法体一律抛「不该被调用」），`org.json` 直接走 SDK 的 `android.jar`（classpath），
> 不自己写桩。

#### 端到端套件

```

```

### §34 v1.10：手机上「源管理」里的菜单项点了没反应

**用户反馈**：手机上源管理，「从剪贴板导入」和「屏上输入」鼠标点击没反应。

**根因不是这两项特殊，是整个浮层从来没绑过任何点击事件。**
菜单项和屏上键盘全都是**纯键盘驱动**的：靠 `CustomActivity` 把遥控器
DPAD/OK 翻译成 `key('UP'/'DOWN'/'OK')`，页面这边只处理按键语义。
电视上遥控器把一切都代劳了，这个洞在电视测试里**永远看不见**；
手机上没有遥控器，于是所有只能手点的项一个都点不动。

实测证据（手机 API 36，CDP 派发真实 touch 序列）：
`.mg-item` 上 `onclick === false`，touch 事件确实命中了 `.mg-key`
（`elementFromPoint` 命中链 `kb-key → kb-row → kb-rows → mg-card → #ysp-manage`），
但 `menuIndex()` 不动、toast 不变 —— 点了跟没点一样。

修法（`custom.js` + `custom.css`）：

| 改动 | 为什么 |
|---|---|
| 菜单项加 `data-i`、键盘键加 `data-r/data-c`，浮层上做**点击委托** | 菜单/键盘每次 `buildMenu/buildKb` 都整块重建，绑在子元素上会失效 |
| 语义定成「点哪一项 = 跳到那一项 + 立刻执行」 | 手指已经落在某一项上了，再要求按一次没有物理位置的确认键，在触屏上是对应不上的动作 |
| `#ysp-manage` 加 `touch-action: manipulation` | 不设的话 Android WebView 会等 300ms 才派发 click，快速连点还会被判成缩放 |
| `.mg-list` 加 `touch-action: pan-y` | 否则快速轻扫被浏览器猜成缩放，菜单滑不动 |
| `@media (hover: none)` 触摸设备专用布局：卡片 92vh、地址块压扁一行、行高略降、`:active` 按下反馈 | 见下面「手机上菜单只有 3 行」那条 |
| `pointerdown` 立刻响应，紧跟的 `click` 丢掉 | 不去重的话「清空全部源」这种两段式动作会在一次点击里直接执行掉，中间的确认等于没有 |

#### 顺手翻出来的三个真问题

**① 局部变量 `key` 遮蔽了同名函数（最难查的一个）**

```js
function onKbClick(e) {
  var key = e.target.closest('.kb-key');   // ← 这个 var 遮蔽了下面的 function key(name)
  kb.r = r; kb.c = c;
  key('OK');                                // ← 实际是「拿 DOM 元素当函数调」→ TypeError
}
```

表现极具迷惑性：**菜单项点击照常工作，只有键盘完全失灵**，而抛出的
`TypeError` 被 WebView 吞掉、连 logcat 都看不到。中间花了很久才定位到，
因为「点菜单有效、点键盘无效」看上去像是 CSS 或坐标问题。
修法：局部变量改名 `keyEl`，并加了一条静态守卫（§验证矩阵里那条
「onKbClick 里的局部变量不叫 key」）—— 局部变量与函数重名这种事，
必须让机器帮我们盯住。

**② 手机上菜单只有 3 行是能看见的，后面几项【根本点不到】**

`.mg-card` 是 84vh，头部两组地址又吃掉一大截，`.mg-list` 只剩 123px ≈ 3 行。
8 项菜单里「清空全部源」在 `top=416`，落在可视区 `[205,328]` 之外 ——

### 29. ⚠️「自定义源」为什么必须有一个**看得见的**入口（v1.5.1）

**起因是一句用户反馈：「还是没有看到 自定义源的 功能」。**
而功能一直是好的 —— `adb shell am start -n com.ysptv.player/.CustomActivity` 能起播，
`aapt2 dump badging` 也确实读到第二个 leanback 入口、label 就是「自定义源」。

**根因：Google TV 的桌面会把同一包名的多个 `LEANBACK_LAUNCHER` 入口按包聚合成一张卡片。**
`AndroidManifest.xml` 里两个 Activity 各自注册了 leanback 入口，桌面却只显示
一张「央视频TV」——「自定义源」那张卡片根本不出现（不是所有桌面都这样，Google TV 是）。
剩下两个入口（蓝键、菜单键长按 0.7 秒）又都是「要按对键才生效」的隐藏操作。
**结论：缺的不是功能，是一个打开面板就看得到的入口。**

于是 1.5.1 在选台面板顶部（tab 与频道列表之间）钉了一行常驻入口：

| 约束 | 为什么 |
|---|---|
| **必须放在 `LIST_SEL`（`.tv-main-con-r-list-left`）之外** | 放进去就会被 `rows()` 当成第 0 个频道 —— 换台、删除、计数、整行对齐滚动全乱 |
| `flex: 0 0 auto` | 不参与列表滚动，永远可见 |
| 高度 7vh（比频道行略矮） | 一眼看上去是「另一类东西」，不是第 0 个频道 |
| 只在**有 `yspBridge` 的页面**出现（`entryWanted()`） | 自定义源页**故意**复用 `inject.js`（`custom.html` 造了一样的 DOM 形状好复用面板），那边再挂一个「自定义源」入口是自指，而且它没有 `yspBridge`，点了只会报错 |
| 「已在第 0 台、再按一次上」才进入口 | 不能写成 `idx + d < 0` —— 那样 `move(-99)` 这种大跨度回顶也会被算成「到顶了」，语义就变了 |

打开它走的是新加的桥方法 `yspBridge.openCustom()`（无参 void，
`addJavascriptInterface` 按**方法名 + 参数个数**精确匹配）；桥方法跑在
JavaBridge 线程上，所以必须 `ui.post()` 再 `startActivity`。

#### ⚠️ 这一版踩到的最阴的一个 bug：无限微任务循环

光标停在入口上时，频道行**永远没有焦点**，而观察者的规则是「没有任何行有焦点 → 重画」。
偏偏 `DOMTokenList.remove()` 按规范会**无条件走一遍 update steps**
—— 即使那个 class 本来就不在，也会把 class 属性重写一遍。于是：

```
重画 → clearFocus 给 40 行各写一次 class → 观察者触发 → 没有行有焦点 → 重画 → …
```

**现象：渲染进程 107% CPU 空转，CDP 的 `Runtime.evaluate` 永不回包，logcat 里一个异常都没有。**
看起来和「App 崩了」一模一样，但进程活着、转发也在。
（暂停栈抓出来落在站点自己的 `hls.cmg.js` 里，极具误导性 —— 真正的循环在微任务队列里。）

两道防线，缺一不可：

1. `clearFocus()` **先 `contains()` 判断、再摘**（从根上掐断，不再无谓地写 class）
2. 观察者回调里 `if (onEntry) return;`（光标在入口上时频道行本来就不该有焦点）

回归断言：`custom_source_test.mjs` 静态段钉住这两条（都是**正向**正则，能真的匹配上）；
`device_test.mjs` 第【14】组额外量了一次 `Runtime.evaluate('1+1')` 的**往返耗时**
—— 只有「页面还答不答话」能测出这种死循环，状态值测不出来。

> **通用教训**：凡是「某处永远没有 X」的新状态（光标在入口上 → 频道行永远没有焦点），
> 都要回头检查「没有 X 就重画」这类自愈逻辑会不会变成无限循环。

### 31. ⚠️ v1.7 换台节流：修「连按上下键会把**站点播放器永久敲死**」

用户原话：「改成 rust 的程序吧，java 运行的时候有点卡，尤其是按上下选台的时候。」

先量再改。用 CDP + 性能时间戳打点，把一次按键拆开：

| 阶段 | 实测 | 归谁 |
|---|---|---|
| 按键 → Java 桥 → `move()` 执行完 | **3–30 ms** | 我们的代码 |
| 站点 SPA 调度 + hls.js 装载 → `loadstart` | 400–600 ms | 央视频页面 |
| m3u8 + 首个 ts 分片下载 | ~550 ms | 网络 |
| MSE 缓冲 + 解码 → 首帧 `loadeddata` | ~600 ms | 站点播放器 |
| **合计（按键到出画）** | **1.5–1.9 s** | |

`Runtime.evaluate('1+1')` 的桥往返只有 **2–3 ms**。**我们自己写的部分占 0.4%，
剩下 99.6% 是站点 JS 排期 + 直播流重缓冲。** 所以「卡」不是 Java 的锅，
换 Rust 一毫秒都省不下来。（这条结论本身记在这里，免得下次再被同样的问题带跑。）

但顺着这条线挖下去，挖出了一个**比"卡"严重得多的真 bug**：

#### 31.1 站点播放器会被快按永久敲死

站点用自研的 **WASM HLS 播放器**（`hls.cmg.js`）播直播。抓控制台报错，
快按换台时会看到：

```
TypeError: Cannot read properties of null (reading 'length')
    at jB.<computed> [as moduleActive] (hls.cmg.js)
    at jE.<computed> [as detachMedia] (hls.cmg.js)
```

`detachMedia → moduleActive` 读了一个 null 的 `.length` 直接抛异常，
把「卸旧源 → 挂新源」这个序列**拦腰截断**：`video.src` 已经被清掉，
新源永远挂不上。后果：

- `video.readyState = 0`、`networkState = 0`、`src = ""`、`currentTime = 0`
- **再点任意一行、按任意键都救不回来**（UI 的选中态照常跳，画面永远黑着）
- 只有 `location.reload()` 能复活
- 全程 logcat 干净、进程不崩、页面还响应 —— 极难第一眼发现

概率实测（`tools/wedge_clean.mjs`，冷启动 → 等真正播起来 → 120ms 连按 6 次）：

| 组 | 死亡率 | 每轮控制台报错 |
|---|---|---|
| 修复前（等价于关掉阀门） | **3/16（19%）** | 4–10 条 |
| 修复后（阀门 1500ms） | **0/16** | 2 条（良性） |

> ⚠️ 方法论教训：这个实验台我写废了两版。第一版在**列表末行**按 DOWN，
> `clamp` 全吃掉、一个换台都没发生，却报告「0/8 没敲死」；第二版用
> `location.reload()` 复位，而站点在程序化 reload 后**不肯自动播**（无用户手势），
> 6 轮全部误判成「起不来」。**前提不校验，结论全是假的。**

#### 31.2 修法：两次发车之间留够站点走完卸/挂序列的时间

`tools/inject.js` 里加了一道阀门（`SWITCH_GAP_MS = 1500`，取自实测首帧 1.3–1.6s）：

- **单次按**：阀门只对"上一次发车"生效，所以**零附加延迟**（实测 201–405ms 内站点就跟着变）
- **连按**：第一按立刻发车，后续按只更新目标、不叠发；到点直接落到**最后想要的那一台**
- 光标 `idx` 始终跟着按的次数走（连按 5 次 → idx +5），不会吞按键
- 按回当前正在播的那一台 → 撤掉待发车（不做无用功，也少惊动站点播放器）
- 切 tab 会撤掉上下键攒的待发车，并把阀门一起压上（左右快依照样能敲死）
- 确认键选中行走同一条阀门

#### 31.3 触摸路径查过了，暂时不用改

手机端有两条换台路径：**上下滑动**走 `move()`，**已被阀门保护**；
**点具体行**走浏览器原生 click，绕过阀门。实测（`tools/tap_probe.mjs`，
冷启动 → 能多快多快地「点行 → 点屏幕重开面板」× 8 轮 × 4 次试验）：**4/4 全部存活**。

原因是这条路径有自限性：点完一行面板就收起，必须再点一次屏幕才能点下一行，
实际节奏慢于站点的卸/挂窗口。**结论是"实测安全"，不是"保证安全"** ——
哪天在手机上碰到黑屏，第一嫌疑就是它。

#### 31.5 ⚠️ 判死必须"连续多次采样都死"

换台途中站点要卸旧源、挂新源，`readyState` 掉到 0 的窗口实测有 **1.3–1.6s**。
按 500ms 采样，**单次采到 `rs=0` 就宣布死亡，会被合法换台骗到**——
我在测试里连骗两次（报"播放器持续死亡"，实际播得好好的）。
现在统一用「连续 6 次采样（约 3 秒）都死」才算死，3 秒是实测重 sourcing 上限的约两倍。

#### 31.6 B 路径调研结论：自研播放器可行，但性价比要看想要多快

用户问「能不能改成 Rust 的」。顺着 latency 拆解查到底，结论分三层：

**第一层：流本身是开放的**（`tools/url_probe.mjs` / `url_probe2.mjs`）

```
https://mobilelive-play.ysp.cctv.cn/ysp/<200位hex>/<流名>_fhd.m3u8?svrtime=…&pid=…&ysign=…&ytime=…
```

curl 实测：**删掉 `ysign`、不带 Referer、不带 cookie，全部 200**；ts 分片直接可拉
（1.37 MB，`video/MP2T`）；`ytime` 改晚一小时也 200。**签名是装饰性的。**

**第二层：播放地址的获取链路是明文的，可以"窃听"**（`tools/eavesdrop.mjs`）

换台时页面自己会打两个接口：

```
POST player-api.yangshipin.cn/v1/player/auth
     body: pid=600001800&guid=…&appid=ysp_pc&rand_str=…&signature=<32hex>
     →  {"token":"s84YElTWJ0q0APrgROyxeGTuPWVVYBnh4mA/5fr3EoHiV73lqTyba14YV8edRJh8…","ts":"…"}
POST player-api.yangshipin.cn/v1/player/get_live_info
     body: {"cnlid":"2024075401","livepid":"600001800","stream":"2","guid":"…","cKey":"--01C7C2…"}
     →  data.backurl_list[0].url = "https://bktlivecloud-cdn.ysp.cctv.cn/<token>/2024075403_web.m3u8?…"
```

在页面里 hook `XMLHttpRequest` 就能把 `backurl_list[0].url` 原样读出来 ——
**不需要逆任何算法**。（⚠️ 这套调用走的是 **XHR 不是 fetch**，只 hook fetch 一条都抓不到。）

**第三层：但自己复刻这套接口 = 逆三层签名，不划算**（`tools/hdr_probe.mjs` / `api_replay.mjs`）

原样重放抓到的请求体，服务端一律 **401 空响应**。缺的是这一堆头：

```
yspsdksign:  <md5>-<ts>-<guid>-<seqId>-<requestId>      ← 五段拼接签名
yspsdkinput: <32hex>
yspPlayerToken / yspplayertoken: <auth 返回的 token>
yspticket:   <长 hex>
request-id / seqId / cookie(guid=…; vplatform=109; …)
```

链路是 `auth.signature → token → cKey → yspsdksign/yspticket`，**大半在 WASM 里**
（`hls.cmg.js`）。按周算的逆向工程，而且站点一更新就全废。

调用栈也帮不上忙（`tools/stack_probe.mjs`）：全是匿名帧
（`G.request → G.post → Function.post`），没有能直接调的命名入口。

**三条路的真实收益（基于上面的实测）**：

| 路线 | 做法 | 换台耗时 | 工作量 | 附加价值 |
|---|---|---|---|---|
| 现状（1.7） | WebView + 站点播放器 + 节流 | 1.5–1.9 s，但不会再把播放器敲死 | 已交付 | — |
| B1 窃听 + 自研播放器 | hook XHR 拿 URL，交给 Kotlin/ExoPlayer | ~1.0–1.1 s（省掉站点 SPA 排期和它的播放器初始化；API 往返和下载省不掉） | 2–3 周 | **彻底摆脱站点播放器的 wedge 病根** |
| B2 预取 | 再进一步：让页面提前解析下一台的 URL | ~0.3 s | B1 + 翻站点打包代码（成本不可预估） | 真正的"秒换台" |
| B3 复刻接口 | 逆三层签名，自己打 API | ~0.3 s | 数周起，且脆弱 | — |

**结论**：B1 值得做的主要理由不是快 30%，而是**从此不再受站点播放器那个
永久 wedge 的 bug 影响**。B2/B3 想要"秒换台"就得啃 minified bundle，
成本不可控，不建议现在投。

### 32. v1.8：自定义源页自己的「＋ 添加自定义源」入口（外加一个 `move()` 的潜在 bug）

**起因还是一句用户反馈：「没有添加自定义源的位置」**，附了张截图：源列表里躺着 5 条示例源，
面板上却找不到任何能往里加东西的入口。

1.5.1 补的入口只在**主界面**的面板上。而自定义源页里「添加」这件事只有菜单键（还有蓝键）
两条隐藏操作 —— 上一版的四条导入路径**全都**要先打开「源管理」浮层，
而浮层本身只有「要按对键才生效」这一种打开方式。
**功能在，但用户找不到 —— 和 1.5.1 之前的主界面是同一个病，换了个页面复发了一次。**

这一版没有新造 UI，而是**把 `inject.js` 已有的入口机制复用到自定义源页，只换动作**：

| 页面 | 判断依据（哪个桥在） | 文案 | 确认键的动作 |
|---|---|---|---|
| 主界面 | `window.yspBridge.openCustom` | 自定义源 · 添加你自己的直播源 | `startActivity(CustomActivity)` |
| 自定义源页 | `window.yspCustom`（且**没有** `yspBridge`） | ＋ 添加自定义源 | 打开本页「源管理」浮层（`__yspUI.openManage()`） |

能这么复用，是因为自定义源页**本来就复用 `inject.js`**：`custom.html` 故意造出一样的
DOM 形状，面板观感 / 整行对齐滚动 / 5 秒自动隐藏 / 触摸手势全部原样复用，入口机制本来
就在这个文件里（§29）。1.5.1 之所以不挂，**唯一原因是动作自指** ——
在自定义源页里再 `startActivity(CustomActivity)` 毫无意义，点上去只会得到一句
「桥接缺失」。把动作换成「打开源管理」，自指消失，入口就可以挂出来了。
（判定仍然用「桥在不在」而不是判 URL —— 桥不在 = 这个 WebView 打不开 CustomActivity，
入口的动作就只能是源管理。）

原有约束一条没破：**入口仍然在 `LIST_SEL` 之外**（`insertBefore(el, list)`），
所以 `rows()` / `count()` / 整行对齐滚动 / 删除模式全不受影响。
底色在 `custom.css` 里压深到 `rgba(16,16,20,.86)`：主界面那行的 16% 品牌红透明度是给
**站点的深色底**用的，本页入口下面垫的是**视频画面**，亮画面上白字会糊。

#### 顺带修掉一个一直存在的潜在 bug：`move(-9999)` 会把光标粘在入口上

入口条件原来写的是 `d < 0 && idx === 0 && entryEl()`。注释里已经提醒过
「不能写成 `idx + d < 0`」—— 但 `d < 0` 本身就有同一个毛病：
`custom.js` 的 `resetCursor(toTop)` 走的是 `move(-9999)`（切分组、导入完刷新都要经过它），
光标本就在第 0 行时会被误判成「到顶了又按了一次上」→ 粘在入口上下不来。

主页一直没暴露，**仅仅因为** `device_test` 那条 `move(-99)` 用例执行时光标恰好不在第 0 行
（`openPanel()` 会先把光标放到正在播放的那一台）。自定义源页挂了入口之后，
这条路径就从「潜在」变成「天天踩」。收紧成 `d === -1`：**只有单步上键**才算「再按一次上」。

#### 测试怎么跟着翻

| 位置 | 1.5.1 | 1.8 |
|---|---|---|
| 静态段 · 入口出现条件 | 「只在有 `yspBridge` 的页面出现」（不能自指） | 「按桥区分两种页面/两种动作」+ 钉住 `ENTRY_TEXT_ADD` / `entryIsAdd()` |
| 静态段 · 入口条件 | `d < 0 && idx === 0` | `d === -1 && idx === 0` |
| 运行时段 · 自定义源页 | `has === false && wanted === false`（**不许**出现） | `has === true && wanted === true`，且是添加变体、仍在列表之外 |
| 运行时段 · 新增 | — | ① `move(-99)` 回顶落在第 0 行不误进入口 ② 第 0 行按上键进入口 ③ 入口上按确认打开源管理（首项 = 局域网导入） |

> **教训（和 §29 同一个根）**：凡是「上一版靠某个前提不成立而侥幸没炸」的逻辑，
> 一旦那个前提被改动（这里是「自定义源页不挂入口」），侥幸立刻变成真 bug。
> `d < 0` 和 `idx + d < 0` 只差一个 `idx === 0`，但后者有注释提醒、前者没有。

## 已知限制

### 通用
- **Android 7.0 以下（API ≤ 23）从 1.6 起装不上**（`minSdk 24`），
  安装阶段就会被拒（报「解析程序包时出现问题」）—— 这是**预期行为**，不是 bug。
  原因：央视频直播要 MSE + WebAssembly + fetch，最低 **Chrome 57**（2017 年）；
  7.0 起 WebView 才是能独立更新到足够新版本的 APK。
  （更早的两档：4.4 从 1.5 起装不上，5.0/6.0 从 1.6 起装不上。详见 §15。）
- 「装得上 ≠ 看得了」这个中间态 **1.6 起不存在了**：7.0 以下直接装不上，
  装得上的内核都远高于 Chrome 57；原来那页「本机内核不支持」的说明也已删除。
- 流媒体地址由站点动态下发，站点若改版 DOM 结构，需同步更新 `inject.css` / `inject.js`。
- 部分付费/版权内容需要登录央视频账号，本 App 不含登录引导。
- `AndroidManifest.xml` 里放开了 cleartext，因为部分直播 CDN 分片走 http。
- release 包**关闭了 WebView 远程调试**（按 `FLAG_DEBUGGABLE` 自动判断），
  所以 CDP 类测试脚本只对 debug 包有效。
- ⚠️ **站点自己的播放器有个我们修不了的竞态**：快按换台时它的 `detachMedia`
  会抛 TypeError 把播放器永久弄死（黑屏、点哪都没反应）。1.7 的换台节流把
  触发概率从约 1/5 压到 0/16 实测，但**没有根治** —— 病根在站点代码里。
  万一还是碰到黑屏，唯一确认有效的恢复是**杀掉 App 重进**（页面 reload 也行，
  但 reload 后站点不自动播、还得再按一次键）。详见 §31。
- ⚠️ **手机上「点具体频道行」这条换台路径没有节流**（走浏览器原生 click，
  绕过了 `move()` 的阀门）。实测 4/4 存活（§31.3），但这是"实测安全"不是"保证安全"。
  哪天在手机上碰到黑屏，第一嫌疑就是它。

### 自定义源
- **局域网导入没有鉴权**：同一局域网内谁都能读写源列表。缓解措施是服务只在
  「源管理」浮层打开时监听 —— 但这是**降低暴露面，不等于安全**。
  导入功能是给「家里电视 + 自己手机」这个场景设计的。
- **带备用音轨的多音轨流（`#EXT-X-MEDIA`）大概率播不了**，而且失败方式很迷惑（能起播再崩）。
  详见「实现要点 19」与上面那张兼容性表。挑源时避开它。
- **fMP4（`#EXT-X-MAP`）需要 Android 8+**；老盒子基本别指望。
- 播放走的是**系统自带的** HLS 解封装，能不能播最终取决于设备 SoC 的编解码器。
  同一台设备上「央视频能播」不代表「这条源也能播」，反之亦然。
- 起播等不到画面会在 **15 秒**后报错（而不是一直转圈）。报错页可以按确认重试。
- 源列表上限 **2000 条**（`M3uParser.MAX_ITEMS`），局域网导入的单次请求体上限 **4 MB**。
- ⚠️ **模拟器上 mediaserver 不可靠**：本机这台 API 34 TV 模拟器上，
  某些流会让 mediaserver 崩溃（`onError what=100`）。真机上罕见得多。
  代码已经能从这种状态里恢复（`rebuildVideo()`，见 §18），
  但**别把模拟器上的 `what=100` 当成 App 的 bug 上报**。
- ⚠️ **有一类流，模拟器就是起不来，而它其实是好的**。已知样本：
  `http://120.198.95.220:9901/tsfile/live/1016_1.m3u8?key=txiptv&playlive=1&down=1`（清单里叫 CCTV2）。
  判定它不是 App 问题的依据（都在 README 的 iptv 那一节里，可复现）：
  宿主取清单 **200** 且是合法 HLS、取第一个分片 **200** 且开头是 TS 同步字节 `0x47`、
  **同一个 host:port 上的 CCTV1 / CCTV3 在设备上正常出画**。
  这类 9901 批次的流还有个共性：分片清单里带着 `##EXT-X-VERSION:3`（双井号）这种不规范标签。
  → 属于 simulator 的 framework MediaPlayer 偏脆，不在 App 控制范围内。
- ⚠️ **源管理浮层一次只看得见 4 行**（头部要显示局域网地址 + 记住的清单地址两组信息，
  卡片高度封顶 84vh）。现在的处理是：光标走到哪一行、那一行一定在可见区内（§22），
  并且底部有「▼ 下面还有 N 项」+ 边缘淡出（§24）。
  能用，但不算好 —— 「一眼看全 8 项」做不到。见「下一步」最后一条。
- ⚠️ **「刷新远程清单」是合并去重，不是同步**。App 里没有「这条源是从哪份清单来的」
  这个概念（`Source` 没有来源字段），所以做不到「把上次这份清单带来的、这次已经不在
  清单里的条目删掉」。要清干净就是「清空全部源 → 再刷新」两下的事。
  详见「实现要点 21 ⑥」。
- **抓取有 6 秒连接 + 12 秒读的上限**（`SourceImport.PROBE_*`）。超时就按「没抓到清单」
  处理 —— 地址仍然会被当成一条源收下，只是那份清单**这次**没导进来。
  慢网/大清单（>2 MB）都可能撞上这条线：慢网重试一次即可，超 2 MB 的清单会被直接拒掉。
- **清单编码只覆盖 UTF-8（含 BOM）/ GBK / GB18030 / GB2312**。
  Big5、不带 BOM 的 UTF-16 这类没处理（前者会按 GBK 试解，多数情况下会得到乱码台名）。
  抓回来是乱码台名时，`node tools/iptv_list_probe.mjs <清单URL>` 能先帮你看出编码。
- **抓取时 HTTPS 证书有问题就直接失败**（`SSLException`），没有「忽略证书」的开关 ——
  这类开关不该出现在一个只管播电视的东西里。真实清单里确实有一条是证书过期。
- **镜像顺延有上限：一轮最多试 4 路、最多 40 秒**（`Mirrors.MAX_ATTEMPTS` / `WALK_BUDGET_MS`）。
  真实清单里最多的一个台有 8 路（CCTV-14），所以确实存在「还有没试过的地址就收手了」的情况。
  只是再加下去用户等不起（实测单次失败约 5 秒）。下一轮顺延会从没试过的那几路接着挑。
- **镜像顺延靠台名归档，台名写法差太远就归不到一起**。归一化处理了大小写、全角、
  分隔符、画质后缀（`CCTV1` / `CCTV-1` / `CCTV-1 (720p)` 算同一个台），
  但 `CCTV-4` 与 `CCTV-4 中文国际` 是**保守地不合并**的 —— 宁可少退一路，
  也不冒「退到另一个台」的风险。详见「实现要点 25」。
- **没有台名的源不参与镜像顺延**（直接粘一个裸地址进来就是这种情况）。
  这是刻意的：匿名源之间互相顺延会变成「点 A 播出 B」。见 §25。
- 死链的失败结果目前只在**本次会话内**记着（页面里的 `bad` 对象 + Java 侧的 `sessionBad`），
  重启 App 就忘了。见「下一步」。

#### 下一步（按性价比排，都还没做）

1. **给 `Source` 加来源字段，把「刷新远程清单」变成真同步**：现在刷新只合并、
   不删已经不存在的条目（见上面那条限制）。做法是导入时记下来源清单的地址，
   刷新时把「这条清单以前带来的、现在不在清单里的」删掉。
   代价是要改 `SourceStore` 的存储格式（加一个字段 + 兼容老数据）。
2. **把「源管理」的信息层级压一压**，让它一次看得见更多项：现在头部两组地址
   （局域网地址 + 记住的清单地址）各占两行，8 项菜单只能看见 4 项。
   思路是把「已记住的清单地址」缩成一行 + 省略号（需要时再展开），
   或者在菜单项多于 N 时把两组地址折叠成一行摘要。§22 只解决了「光标可见」，
   §24 只解决了「知道下面还有」，**都没解决「一眼看全」**。
3. 死链的失败结果目前只在**本次会话内**记着（页面里的 `bad` 对象 + Java 侧的 `sessionBad`），
   重启 App 就忘了。可以落盘成「最近一次失败时间」，让用户一眼看出哪些源该清掉。
   顺带能让镜像顺延跨会话记住「哪几路是死的」，一开机就跳过它们。
4. 局域网导入页可以再加一个「刷新」按钮直接改已记住的地址（现在要重新粘一次新网址）。
5. **镜像顺延目前不告诉用户「它跳过的那几路为什么被跳过」**。现在的排序是
   「本次会话没失败过的优先」，规则没出现在任何界面上。可以做一行说明，
   或者干脆按画质排序（1080p 优先），让顺延的落点更符合直觉。
